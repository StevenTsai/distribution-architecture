# 接手工程方法论 v0.1

> **文档定位**：工具箱总纲。定义「接手工程」的适用边界、四条原则、六阶段模型、阶段闸门与质量判据。
> **状态**：已随本仓库发布 ｜ **日期**：2026-10-18 ｜ **版本**：v0.1

---

## 一、什么是接手工程

**接手工程（Takeover Engineering）**：在一套已经存在、但不完全可控的系统中，完成「评估 → 决策 → 重建 → 证明」的工程方法。

它和常规项目管理的根本区别：

| 维度 | 从零建设项目 | 接手工程 |
|---|---|---|
| 起点假设 | 需求清楚、团队可控、代码归零 | 资产不全、文档失真、代码未知 |
| 首要任务 | 设计与实现 | 取证与判断 |
| 最大风险 | 需求变更 | 隐性债务与责任错配 |
| 成功标准 | 按期上线 | 先证明「该不该接、做到什么程度」 |
| 决策频率 | 里程碑 | 每个阶段都有止损闸门 |

### 适用场景

- 接手外包做了一半的项目；
- 接手离职团队留下的系统；
- 收购、并购、重组后的技术资产盘点；
- 遗留系统现代化改造前的评估；
- 自有系统在重大演进前的基线确认。

### 不适用场景

- 需求与资产都完全可控的新建项目；
- 只做一次性技术咨询、不承担交付的情况（可裁剪使用 01–03）。

## 二、方法的四条原则

### 原则 1：证据分级（Evidence Grading）

任何结论都必须标注证据等级。**没有等级的判断，默认视为推断。**

| 等级 | 名称 | 判定标准 | 可用于 |
|---|---|---|---|
| **E1** | 源码实证 | 直接读到实现，且能定位到文件/行 | 报价、承诺、验收 |
| **E2** | 运行实证 | 可复现地跑通/抓包/观察到行为 | 报价、承诺、验收 |
| **E3** | 文档/契约 | 有书面文档或接口契约，但未验证实现 | 估算、待验证项 |
| **E4** | 推断 | 根据行为、命名、日志反推，未验证 | 仅限风险项，不得作为承诺 |
| **E5** | 假设/新建 | 各方口头共识，或需要全新实现 | 必须写入假设清单与前置条件 |

**硬规则**：

- 报价中的工作量，只能建立在 E1–E3 上；E4/E5 必须单列风险准备金；
- 对外承诺「已实现」的，必须至少 E1 或 E2；
- 任何 E4 结论进入交付，必须先升级为 E1/E2，否则不得关闭；
- 证据等级要写进报告，不能只写结论。

---

### 原则 2：三落点（Three Anchors）

每个 P0/P1 风险项，必须同时落到三个位置：

```
风险项 ──┬── ① 合同/商务落点：条款类别、前置条件、责任归属
         ├── ② 代码落点：约束条件、校验、边界处理
         └── ③ 测试落点：守护测试、回归用例、失败即阻断
```

**缺任意一处，该风险项不得标记为「已闭环」**：

- 只有合同、没有代码 → 出事仍然扯皮；
- 只有代码、没有测试 → 下次改动静默回归；
- 只有测试、没有合同 → 测试通过也无法界定责任。

三落点不是形式主义，它回答三个不同问题：**谁承担、怎么防、怎么证明。**

---

### 原则 3：两端夹逼（Two-End Squeeze）

验证契约时，不要只做「客户端 × 假后端」或「假客户端 × 真后端」。必须让**真实的两端互相打**：

```
真实客户端 ──契约──> 真实服务端
     │                    │
     └── 任何一端不守契约，测试变红 ──┘
```

补充手段：

- **独立第二实现**：用另一种语言/框架实现关键算法，逐位对拍（平台原生实现可作仓外裁判）；
- **契约冻结**：接口字段、错误码、枚举顺序以客户端实际消费为准，不按文档「优化」；
- **失败矩阵**：对每个接口列出超时、重试、幂等、部分失败的行为。

**判据**：测试能指出「是哪一端不守契约」，而不是只报「断言失败」。

---

### 原则 4：止损前置（Exit Before Start）

在项目开始前，就把「什么情况下停」写清楚：

| 要素 | 必须写明 |
|---|---|
| 触发条件 | 资产未交付、授权不明、关键依赖缺失、需求持续漂移、付款违约、责任边界无法收敛 |
| 分级 | 观察 / 降级 / 暂停 / 终止 |
| 决策人 | 谁有权拍板，谁必须知情 |
| 时限 | 触发后多少工作日内决策 |
| 结算 | 已发生工作量如何计算、成果权利如何处置 |
| 收尾 | 资产归还、代码封存、文档归档、对外口径 |

**没有止损条款的项目，不是「更稳定」，而是「更贵」。**

## 三、六阶段模型

```
取证 ──> 量化 ──> 划界 ──> 定价 ──> 重建 ──> 证明
 │        │        │        │        │        │
 └────────┴────────┴────────┴────────┴────────┘
              每阶段末：止损闸门
```

### 阶段 1：取证（Forensics）

| 项 | 内容 |
|---|---|
| 核心问题 | 这套系统到底是什么状态？ |
| 输入 | 源码、构建产物、运行环境、账号、文档、设备/数据 |
| 动作 | 资产盘点、构建验证、静态走查、运行验证、契约核对 |
| 输出 | 资产清单、取证报告、缺失物清单、健康检查结论 |
| 闸门 | **证据不足不得进入量化。** 拿不到源码/构建/运行三者之二，只能做「有条件评估」 |
| 模板 | `templates/01-asset-inventory.md` |

**关键动作**：

1. 先验证「能不能构建」，再读代码；
2. 先验证「线上跑的是不是这份代码」，再谈复用；
3. 所有缺失物写成清单，而不是记在脑子里；
4. 对每个结论标 E1–E5。

---

### 阶段 2：量化（Quantify）

| 项 | 内容 |
|---|---|
| 核心问题 | 范围多大、能复用多少、缺多少？ |
| 输入 | 取证报告、需求/界面/接口清单 |
| 动作 | 需求盘点、复杂度五维评分、复用度四分类、缺口台账 |
| 输出 | 复杂度表、复用度表、缺口与风险台账 |
| 闸门 | **无法量化不得报价。** 待确认项超过总量的 15%，报价只能给区间 |
| 模板 | `templates/02-reuse-assessment.md`、`templates/03-gap-risk-ledger.md` |

**五维复杂度评分**（1–5 分，可调整权重）：

| 维度 | 看什么 |
|---|---|
| 业务规则 | 状态机数量、分支、例外、边界条件 |
| 集成广度 | 设备/第三方/多端/多品牌/多环境 |
| 数据复杂度 | 实体数量、关系、迁移、一致性要求 |
| 非功能约束 | 性能、安全、合规、可用性 |
| 不确定性 | 缺口数量、待确认项、外部依赖 |

**复用度四分类**：

| 分类 | 判定 |
|---|---|
| 完整复用 | 功能与验收标准均满足，仅需回归 |
| 部分复用 | 主体可留，但需改造、补测或补契约 |
| 纯新增 | 存量中没有，需从零实现 |
| 待确认 | 证据不足，需进一步取证或客户确认 |

---

### 阶段 3：划界（Boundary）

| 项 | 内容 |
|---|---|
| 核心问题 | 谁负责什么？软件明确不做什么？ |
| 输入 | 需求、硬件/固件能力、第三方平台限制 |
| 动作 | 责任方矩阵、数据权威源确认、安全边界声明、前置条件清单 |
| 输出 | 职责边界矩阵、边界确认稿、承接前置条件 |
| 闸门 | **边界不收敛不得签约。** 关键边界项未书面确认，合同应附「待确认清单」并约定时限 |
| 模板 | `templates/04-responsibility-matrix.md` |

**必须写清的边界**：

- 软件是「展示与操作辅助」，还是「安全装置」；
- 数据以谁为准：设备、云端、第三方平台、人工录入；
- 哪些指令由软件转发，哪些由固件/硬件自主执行；
- OTA 的内容、签名、回滚由谁负责；
- 平台限制（后台运行、定位、并发、审核规则）算谁的责任；
- 事故处理流程：通知、取证、鉴定、费用。

---

### 阶段 4：定价（Price）

| 项 | 内容 |
|---|---|
| 核心问题 | 多少钱、基于什么假设、风险溢价多少？ |
| 输入 | 量化结果、边界矩阵、前置条件 |
| 动作 | 模块拆分、逐项人日、风险准备金、假设清单 |
| 输出 | 报价模型、价格有效期、前置条件 |
| 闸门 | **前置条件未满足不得锁定价格**；价格必须写明有效期与假设 |
| 模板 | `templates/06-pricing-model.md`、`templates/03-gap-risk-ledger.md` |

**定价结构建议**：

```
报价 = 基础模块（可审计人日）
     + 复用改造（按四分类逐项）
     + 新增模块
     + 风险准备金（E4/E5 项）
     + 外部依赖成本（设备、账号、第三方）
```

**三条纪律**：

1. 每个数字能追溯到模块和人日；
2. 假设变化必须触发价格重算；
3. 不接「总价包死 + 范围不清」的单。

---

### 阶段 5：重建（Rebuild）

| 项 | 内容 |
|---|---|
| 核心问题 | 怎么在契约约束下实现？ |
| 输入 | 接口契约、验收基线、边界矩阵 |
| 动作 | 契约先行、分层标注、适配层隔离、失败矩阵 |
| 输出 | 重建方案、接口契约、实现与契约对照 |
| 闸门 | **契约未冻结不得开工。** 契约变更必须走变更记录 |
| 模板 | `templates/07-contract-first-rebuild.md` |

**实现纪律**：

- 每个接口标注来源：`[源码]` / `[运行]` / `[推断]` / `[新建]`；
- 行为原样优先：错误文案、枚举顺序、分页默认值不擅自「优化」；
- 外部依赖用适配层隔离，保证无硬件/无后端也能开发与演示；
- 为每个接口写失败矩阵，而不是只写成功路径。

---

### 阶段 6：证明（Prove）

| 项 | 内容 |
|---|---|
| 核心问题 | 怎么证明做对了？ |
| 输入 | 测试、审查记录、验收标准 |
| 动作 | 分层测试、守护测试、追溯矩阵、as-built 对照 |
| 输出 | 测试报告、质量台账、验收包、as-built 文档 |
| 闸门 | **红线测试不绿不得交付**；未验证项必须如实标注 |
| 模板 | `templates/08-acceptance-traceability.md`、`templates/09-quality-review-ledger.md` |

**证明体系**：

| 层级 | 证明什么 |
|---|---|
| 单元测试 | 逻辑正确 |
| 契约测试 | 两端互认 |
| 端到端测试 | 主链路可用 |
| 守护测试 | 红线不被侵蚀 |
| 静态检查 | 规范与安全基线 |
| 对拍测试 | 独立实现一致 |
| 追溯矩阵 | 需求 → 设计 → 代码 → 测试 → 验收 无断点 |

**诚实边界**：全绿 ≠ 真机通过；无硬件时，必须写明「未验证项」与验证计划。

---

## 四、阶段闸门与止损

每个阶段结束前，回答三个问题：

1. 本阶段的输出是否达到质量判据？
2. 未关闭的风险项是否在可接受范围内？
3. 是否触发止损条件？

| 闸门 | 不通过时 |
|---|---|
| 取证 → 量化 | 只能做「有条件评估」，不报价 |
| 量化 → 划界 | 不给总价，只给区间与假设 |
| 划界 → 定价 | 不锁定价格，合同附待确认清单 |
| 定价 → 重建 | 不启动开发，或按「评估 + 预研」计费 |
| 重建 → 证明 | 不进入验收，先补契约与测试 |
| 证明 → 交付 | 不交付，先关闭 P0 项 |

止损分级与动作见 `templates/05-exit-checklist.md`。

## 五、角色与时间盒

| 角色 | 职责 | 接手中最容易被忽略的事 |
|---|---|---|
| 决策者 | 接不接、停不停、签不签 | 把「再等等」当成决策 |
| 技术负责人 | 取证、量化、划界、重建 | 把「能跑」当成「可维护」 |
| 商务 | 定价、前置条件、合同 | 把口头承诺当成范围 |
| 测试/质量 | 证明体系、守护测试 | 把「演示通过」当成验收 |
| 客户对接人 | 资产、确认、验收 | 没有书面确认权 |

**建议时间盒（中小型接手项目）**：

| 阶段 | 评估期投入 | 说明 |
|---|---|---|
| 取证 | 1–3 人日 | 取决于代码规模与构建可复现性 |
| 量化 | 1–2 人日 | 有界面/接口清单时可加速 |
| 划界 | 0.5–1 人日 | 必须与客户共同确认 |
| 定价 | 0.5 人日 | 基于前三个阶段 |
| 合计 | **3–6 人日** | 超过 6 人日应作为独立付费评估 |

## 六、质量判据

一份合格的接手评估，必须满足：

- [ ] 每个结论有证据等级；
- [ ] 每个 P0 缺口有归属、关闭条件与时限；
- [ ] 每个 P0/P1 风险有三落点；
- [ ] 每个报价数字可追溯到模块与人日；
- [ ] 每个待确认项有确认方式与责任人；
- [ ] 边界矩阵经双方书面确认；
- [ ] 有明确的止损条件与决策人；
- [ ] 明确写出「本次评估未覆盖什么」。

## 七、常见失败模式

| 失败模式 | 表现 | 后果 | 对策 |
|---|---|---|---|
| 把「能跑」当「可维护」 | 演示通过就报完整复用 | 后期返工 | 必须做构建与回归验证 |
| 把「文档有」当「已实现」 | 按文档报价 | 工作量翻倍 | 文档结论标 E3，逐项验证 |
| 把「口头承诺」当「范围」 | 客户说「这个简单」 | 无限追加 | 所有范围进书面清单 |
| 低估多品牌/多端/多环境 | 只按一个样本估算 | 适配成本爆炸 | 用「品牌数 × 差异度」建模 |
| 没有止损点 | 越做越沉没 | 时间和口碑双输 | 签约前写退出条件 |
| 只测成功路径 | 演示很顺，上线出事 | 事故与责任 | 失败矩阵 + 守护测试 |
| 责任边界模糊 | 出事故才讨论 | 扯皮、拒付 | 边界矩阵 + 书面确认 |

## 八、术语

| 术语 | 含义 |
|---|---|
| 证据等级 | E1 源码 / E2 运行 / E3 文档 / E4 推断 / E5 假设 |
| 三落点 | 合同条款、代码约束、守护测试 |
| 两端夹逼 | 真实客户端与真实服务端互测 |
| 复用度四分类 | 完整复用 / 部分复用 / 纯新增 / 待确认 |
| 止损闸门 | 阶段末的继续/降级/暂停/终止决策点 |
| as-built | 以代码为唯一事实源的现状文档 |
| 守护测试 | 防止红线被后续改动侵蚀的测试 |
| 失败矩阵 | 每个接口/流程的超时、重试、幂等、部分失败行为清单 |
