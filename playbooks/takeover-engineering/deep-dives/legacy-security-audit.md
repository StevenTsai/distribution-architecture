# 遗留系统三轮安全审计：46 项发现与一条自噬的限频

> 接手"能跑"的存量系统，先审计再开发。单轮审查一定有盲区，三轮递进加四件套闭环，把"代码已改"变成"证据已复跑"。
>
> 本文提炼自一次真实的软硬一体项目接手（小程序 + 设备 + 后端，前团队交付、快照不完整、无测试无文档）。数字为该项目实录，示例已泛化。

---

## 一、为什么接手后先审计

接手时的系统状态是"能跑、但不敢碰"：

- 无任何单元测试，无 lint/CI 痕迹；
- 生产快照不完整（前后端都缺文件），且做过 URL 脱敏；
- 代码里有调试残留、死代码、四份互相不一致的协议命令表；
- 安全设计上有一批"当时能跑就行"的妥协。

在这种状态下直接叠功能，等于不知道地基承重就加盖楼层。顺序应定为：**先事实盘点 → 再安全审计 → 再协议文档化 → 最后才开发**。审计分三轮递进，绝非一次性动作。

---

## 二、三轮审计机制与四条纪律

| 轮次 | 方法 | 发现 | 特征 |
|---|---|---|---|
| 第一轮 | 外部审计（逐文件走查） | 19 项（P0×4 / P1×5 / P2×10） | 结构性、高危项 |
| 第二轮 | 双端复审（后端 + 小程序分别再审） | 20 项（4 项与上轮重构相关，含 1 项回归） | 抓修复引入的新问题 |
| 第三轮 | 探针复查（11 个黑盒脚本复现） | 7 项（5 确定 + 2 边角） | 验证"真的修好了" |

三轮共 **46 项**，全部闭环。四条纪律贯穿始终：

1. **每项必须有可复跑证据**：测试用例或探针脚本，不接受"代码已改"作为关闭条件；
2. **修复提交按模块拆分**（`fix(backend)` / `fix(miniprogram)` / `test` / `docs`），保证可回溯；
3. **回归用例先行**：红灯 → 修复 → 绿灯；
4. **技术债透明化**：修不了的写进清单，不假装不存在。

最终测试基线从 8 套增长到 12 套，全部全绿。

三轮的分工是这套机制的核心：**单轮审查一定有盲区；复审能抓住"修复引入的回归"；探针复查把"看起来修好了"变成"黑盒复现确认修好了"。**

## 三、三类系统性问题

最危险的不是业务 bug，而是三类系统性问题。它们的共同点是：单看每段代码都"合理"，连起来才有风险。

### 3.1 注入：长度检查挡不住命令拼接

业务层用 `shell_exec` 拼接命令调用外部脚本，而进入调用前的输入**只做了一次长度检查**：长度对了就直接拼进命令字符串，密钥 ID 与参数同样未经转义，全在同一条命令里。

修复有两条路径：

- 短期：`escapeshellarg()` / `proc_open` 数组传参；
- 根本：去掉 shell 依赖，用原生密码学库在进程内实现。这不仅消除注入面，还顺带消除了部署依赖。

### 3.2 凭证：离开控制范围即视为泄露

短信服务的 AccessKey / Secret 以明文写在配置文件里，且生产快照已经流出。判断标准很简单：

> 代码一旦离开你的控制范围，硬编码凭证就等同于已泄露。

处置顺序不能反：**先在云控制台轮换凭证 → 再改环境变量读取 → 最后核查账单与异常调用**。代码修复排在轮换之后，因为改代码不能收回已经流出的密钥。同一轮还收紧了上传白名单（`pem/key/p12/bin` 等敏感扩展名此前可上传）。

### 3.3 认证信任错位：客户端说什么就是什么

登录接口直接信任客户端提交的 `openid`：请求里传谁的 openid，就签发谁账号的 token。openid 不是秘密，它会出现在日志、分享链路和前端存储里。这意味着**知道对方的 openid 就能接管账号**，进而操作其绑定的设备。

修复方案是一次性登录票据（短时效、用后即焚）：

```text
会话登录(code)      → { openid, login_ticket }
票据登录(openid, ticket) → token
```

票据校验覆盖四类异常凭证：无票、坏票、重放（`used` 标记）、票与人错配。还有一个只有踩过才会想到的细节：**失败回滚**。先"预占"票据防并发重放，若下游接口调用失败，回滚为未使用再抛错。否则一次接口抖动就会把票据烧掉，用户被锁死在"登录凭证无效"的循环里。这个回滚是第二轮复审补上的：第一版只做了"用后即焚"，没做"失败归还"。

## 四、限频自噬：一个安全机制废掉另一个

短信验证码有 60 秒发送限频。验证码状态存在一行记录里：验证码、过期时间、尝试次数、上次发送时间。

它还做了常见的安全加固：**连续 5 次输错就作废验证码**。问题在于"作废"的实现是整个删行：验证码、过期时间、尝试次数、上次发送时间一起消失。而上次发送时间正是限频的唯一依据。行被删掉之后，下一次发送请求查不到发送记录，**60 秒发送限频随之失效**。

修复只改了一个语义：**作废 = 保留行、清空验证码与过期时间，绝不动发送时间。** 回归用例锁定修复后的行为：1 秒内连续发送 4 次，只有第一次成功。

这类"机制互噬"的教训可以推广：**安全机制的实现不能共享彼此的生存依赖。** 计数类、限频类、冷却类逻辑审计时必须问一句：这个"清理/作废"动作，会不会连带清掉另一个机制的依据？

## 五、越权：一类接口要成组检查

设备 OTA 有三条链路：查询固件信息、读取升级日志、上报升级结果。原实现里，读取日志、上报结果两条都做了归属校验，但最先写的"查询固件信息"一直裸奔，第三轮探针抓的正是这条"最后漏网"。该接口按设备标识精确查询并返回固件、版本与下载地址，任何人可枚举设备标识读取他人设备信息，属于典型的越权读取（IDOR）。

修复是统一成一个归属校验中间件，不通过就返回业务错误，不落到数据层。经验有二：

1. 一类接口的权限修复要**成组检查**，漏一个等于没修；
2. 权限不能靠人眼 review，要写探针脚本按角色矩阵（用户 A × 用户 B × 资源）自动跑一遍。

## 六、前端状态一致性与 HTTP 边界

审计不只针对后端。前端的四类问题共性是：**UI 状态的"事实"来自多处（本地乐观更新、设备确认、持久化存储），没有单一事实源。** 修复方式是明确优先级：设备确认 > 本地持久化 > 乐观更新，而非在各处加 if 补丁。典型如"解绑被设备拒绝，本地却清空了绑定状态"：设备还绑着，用户以为解绑了。

HTTP 边界则要求**错误要有信封**：

- 非法绝对 URL 让框架把未捕获异常抛成 500，而契约要求所有响应都是 `{code, message, data}` 信封 → 修复为 400 信封；
- 超限的多段上传直接 `destroy()` 连接，客户端只能看到连接重置，拿不到 413 → 修复为丢弃剩余数据、返回 413 信封、兜底断开。

第二条还有一个隐藏考点：**慢速多段上传**。如果实现成"读满 buffer 再判断"，超限请求可以在极长连接里拖住服务端。修复后无论快慢，都在读流过程中尽早返回错误。

## 七、诚实清单：决定不做的事

审计的产出不只是修复，还有一份"已知技术债"。修不了的显式登记：

| 项 | 现状 | 处置 |
|---|---|---|
| 密码学点乘非常量时间 | 未加固（自研实现限制） | 文件头记录限制与建议；验收环境限制接口暴露面 |
| 核心文件过大（近千行） | 闭包状态机耦合高 | **验收前不拆**：回归风险大于可维护性收益，评审后分批重构 |
| 模拟设备精度 | 已兼容主要口径 | 真机抓包后逐帧收紧 |
| 存储 | 单进程 JSON | 长期运行换存储引擎（契约冻结，只换存储） |

"决定不做的事"也要写进记录：不拆文件不是懒，是在验收窗口内对回归风险的判断。**工程决策的质量，往往体现在"什么时候不做"上。**

## 八、可复用检查清单

老系统安全审计的分类清单，按类过，不按文件过：

- **注入类**：所有 `shell_exec / exec / eval / 拼接 SQL` 调用点，检查输入是否只做了长度/类型检查就进入执行路径；
- **凭证类**：全仓 grep `AK / Secret / password / token` 硬编码；快照流出过的凭证一律视为已泄露，先轮换再改代码；
- **认证类**：客户端提交的身份标识（openid / 设备 ID / 用户 ID）是否被直接信任？是否要求服务端签发的一次性凭证？票据是否有防重放与失败回滚？
- **授权类**：按资源分组的接口成组检查归属校验；用角色矩阵探针（A×B×资源）自动跑；
- **计数/限频类**：限频依据与"清理/作废"逻辑是否共享存储行？删除动作是否连带清掉了依据？
- **状态一致性类**：前端乐观更新是否有失败回弹？"服务端确认"与"本地状态"的优先级是否明确？
- **边界类**：非法输入返回统一信封而不是 500/RST；大 payload 在读取过程中尽早拒绝；
- **流程类**：每项发现四件套（发现 / 提交 / 回归 / 证据）；修复提交与文档同步；技术债显式登记。

## 九、诚实边界

- 三轮机制与清单提炼自**单一项目实录**，46 项的构成与该系统的快照质量、前团队交付习惯相关，不构成"遗留系统平均发现数"的基准；
- 三轮的划分依赖第二人参与复审与独立探针脚本；单人接手时至少应做"自查 + 冷藏后复查"两轮，并把探针脚本当作验收条件；
- 本文是工程视角的接手前审查方法，**不能替代专业渗透测试与安全评估**；
- 示例中的修复手段按技术类别泛化，不含该系统的业务逻辑、协议细节与内部代号。
