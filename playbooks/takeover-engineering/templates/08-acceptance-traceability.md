# 模板 08｜验收追溯矩阵

> **阶段**：证明 ｜ **用途**：证明「需求没有被漏掉、代码没有多余、测试没有假装覆盖、验收有据可查」 ｜ **版本**：v0.2
> **原则**：**没有追溯链的「已完成」，只是主观表述。**

---

## 一、追溯链

```
需求（FR / BR / NFR）
   ↓
设计（模块 / 接口 / 数据）
   ↓
代码（文件 / 类 / 函数）
   ↓
测试（用例 / 测试名）
   ↓
验收（验收项 / 证据 / 签字）
```

**两个方向都要能走通**：

- 正向：每条需求都能找到实现与测试；
- 反向：每段关键代码都能回答「为哪条需求存在」。

---

## 二、ID 规则

| 类型 | 格式 | 示例 |
|---|---|---|
| 功能需求 | `FR-{{NN}}` | `FR-01` |
| 业务规则 | `BR-{{NN}}` | `BR-01` |
| 非功能需求 | `NFR-{{NN}}` | `NFR-01` |
| 验收项 | `AC-{{NN}}` | `AC-01` |
| 测试用例 | `TC-{{NN}}` | `TC-01` |
| 缺陷 | `BUG-{{NN}}` | `BUG-01` |
| 缺口 | `GAP-{{NN}}` | `GAP-01` |

**纪律**：

- ID 一旦分配不复用；
- 需求删除时保留 ID，状态改为「已取消」；
- 测试名中带 ID，便于自动统计（如 `test_FR01_...`）。

### 3.1 状态定义

| 状态 | 含义 | 可交付 |
|---|---|---|
| ✅ 已验证 | 实现存在，测试通过，证据可追溯 | 是 |
| 🟡 部分验证 | 实现存在，验证不完整 | 需说明边界 |
| ⏳ 未实现 | 范围外或未完成 | 否 |
| ❌ 明确不做 | 已书面确认不做 | 是（附依据） |
| 🚫 阻塞 | 依赖未满足 | 否 |

**禁止**把「未验证」写成 ✅。

## 四、验收证据

### 4.1 证据类型

| 类型 | 适用 | 强度 |
|---|---|---|
| 自动化测试报告 | 功能、规则、契约 | 高 |
| 真机/现场记录 | 硬件相关 | 高 |
| 截图/录屏 | 界面、流程 | 中 |
| 接口抓包 | 契约、集成 | 高 |
| 人工验收单 | 商务验收 | 高（需签字） |
| 口头确认 | — | **不可作为验收证据** |

### 4.2 证据字段

| 字段 | 要求 |
|---|---|
| 证据编号 | 唯一 |
| 类型 | 上表之一 |
| 位置 | 链接/路径/附件名 |
| 生成时间 | 精确到日 |
| 环境 | 版本、设备、数据 |
| 执行人 | 具体人 |
| 结论 | 通过/不通过/部分通过 |
| 备注 | 未覆盖项 |

---

## 五、覆盖度指标

| 指标 | 计算 | 目标 |
|---|---|---|
| 需求覆盖率 | 有实现的需求 / 总需求 | 100%（不含明确不做） |
| 测试覆盖率 | 有测试的需求 / 有实现的需求 | P0 100%，P1 ≥ 90% |
| 验收证据覆盖率 | 有证据的验收项 / 总验收项 | 100% |
| 反向覆盖率 | 有需求归属的关键代码 / 关键代码总量 | ≥ 90% |
| 未验证项占比 | 未验证项 / 总项 | 如实披露，不设「好看」目标 |

> 覆盖率是**发现断点的工具**，不是对外宣传的数字。

## 六、未验证项登记

> 接手项目一定有未验证项。**写出来是专业，藏起来是风险。**

| ID | 未验证项 | 原因 | 影响 | 建议验证方式 | 责任方 | 计划时间 |
|---|---|---|---|---|---|---|
| UV-01 | 真机 BLE 并发 | 无设备 | 高 | 现场联调 | 客户 | |
| UV-02 | 第三方支付回调 | 账号未开通 | 中 | 沙箱 + 真单 | 客户 | |
| UV-03 | 性能压测 | 范围外 | 中 | 专项测试 | 双方 | |

**未验证项必须进入**：

1. 验收报告；
2. 合同附件或交付说明；
3. 风险台账。

## 七、验收流程

```
自检（内部矩阵）
   ↓
内部评审（测试 + 开发 + 产品）
   ↓
提交验收包（矩阵 + 证据 + 未验证项）
   ↓
客户验收（逐项签字）
   ↓
问题项（缺陷/变更/接受）
   ↓
验收结论（通过 / 有条件通过 / 不通过）
```

### 7.1 验收包清单

- [ ] 需求清单与状态；
- [ ] 追溯矩阵；
- [ ] 测试报告（含失败项与跳过项）；
- [ ] 未验证项清单；
- [ ] 已知问题清单；
- [ ] 部署与回滚说明；
- [ ] 验收单（可签字）。

### 7.2 有条件通过

必须写明：

- 未通过项；
- 补救措施；
- 完成时间；
- 尾款条件；
- 逾期处理。

## 九、质量检查清单

- [ ] 每条需求都有唯一 ID；
- [ ] 每条 P0 需求都有实现、测试与证据；
- [ ] 每个测试名可关联需求 ID；
- [ ] 关键代码能反向追溯到需求；
- [ ] 未验证项如实登记并进入交付说明；
- [ ] 跳过/失败的测试没有被计为通过；
- [ ] 验收证据有环境、时间、执行人；
- [ ] 有条件通过项有补救计划与尾款条件；
- [ ] 矩阵与测试报告数字一致；
- [ ] 验收单可签字。

## 十、常见错误

| 错误 | 后果 | 纠正 |
|---|---|---|
| 用「已完成」代替证据 | 验收时无法举证 | 每个 ✅ 附证据 |
| 测试名不关联需求 | 无法统计覆盖 | 测试名带 ID |
| 跳过测试算通过 | 掩盖风险 | 单列 skip |
| 只做正向追溯 | 死代码与范围蔓延 | 增加反向追溯 |
| 未验证项不写 | 交付后被追责 | 主动登记 |
| 覆盖率造假 | 短期好看，长期爆雷 | 如实披露 |
| 验收单无签字 | 无法作为结算依据 | 逐项签字 |
