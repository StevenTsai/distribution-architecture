# 模板 05｜止损与收尾清单

> **阶段**：全阶段 ｜ **用途**：在项目开始前定义「什么时候停」，在停止时把资产、责任、文档与对外口径一次收干净 ｜ **版本**：v0.1
> **原则**：止损不是失败，是**把损失限制在可承受范围内**。收尾不是结束，是**把这次经验变成下一次的资产**。

---

## 一、止损的三个前提

止损之所以难，通常不是不知道要停，而是：

1. **没有触发条件**——「再等等看」成为默认决策；
2. **没有决策人**——执行者想停但不敢停；
3. **没有收尾预案**——停了之后资产、代码、责任一团乱。

本清单要求：**触发条件、决策人、收尾动作，在项目开始前就写好。**

---

## 二、触发条件

> 每条触发条件必须是**可观察的事实**，不是感受。写「连续 10 个工作日未提供样机」，不写「客户不配合」。

### 2.1 资产类

| # | 触发条件 | 观察方式 | 建议分级 |
|---|---|---|---|
| A1 | 约定时间内未交付源码/构建/环境 | 交付记录 | 暂停 |
| A2 | 源码不完整，且无法补齐 | 构建验证 | 暂停/终止 |
| A3 | 关键账号/权限持续不可得 | 申请记录 | 暂停 |
| A4 | 样机/测试设备未到位，无法验证 | 到货记录 | 降级（只做可仿真部分） |
| A5 | 协议/接口文档缺失，且对方无法提供 | 书面记录 | 降级/暂停 |

### 2.2 授权与合规类

| # | 触发条件 | 观察方式 | 建议分级 |
|---|---|---|---|
| B1 | 原系统权利归属不清，无法书面说明 | 法务意见 | 暂停（签约前） |
| B2 | 要求使用无授权代码/资源 | 审查 | **立即终止** |
| B3 | 要求承诺无法承担的安全/合规责任 | 合同文本 | 暂停（签约前） |
| B4 | 数据处理违反告知同意或留存要求 | 合规审查 | 暂停 |

### 2.3 需求与范围类

| # | 触发条件 | 观察方式 | 建议分级 |
|---|---|---|---|
| C1 | 需求变更累计超过合同范围的 <span v-pre>{{X}}</span>% | 变更记录 | 重新报价/暂停 |
| C2 | 关键需求无确认权人，或确认反复 | 会议记录 | 暂停 |
| C3 | 验收标准持续不可量化 | 验收文档 | 暂停（不进入开发） |
| C4 | 需求方向发生根本变化（目标用户/核心流程） | 书面确认 | 终止或重签 |

### 2.4 商务类

| # | 触发条件 | 观察方式 | 建议分级 |
|---|---|---|---|
| D1 | 付款逾期超过 <span v-pre>{{N}}</span> 天 | 财务记录 | 暂停交付 |
| D2 | 对方要求先交付后补合同 | 书面记录 | 暂停 |
| D3 | 对方提出合同外的新承诺 | 沟通记录 | 拒绝 + 书面澄清 |
| D4 | 出现未披露的第三方权利主张 | 函件 | 暂停 |

### 2.5 技术与质量类

| # | 触发条件 | 观察方式 | 建议分级 |
|---|---|---|---|
| E1 | 关键依赖（固件/第三方）长期阻塞 | 阻塞记录 | 暂停 |
| E2 | 无法在约定环境复现线上问题 | 复现记录 | 降级 |
| E3 | 安全漏洞无法在约定时间内修复 | 漏洞记录 | 暂停上线 |
| E4 | 红线测试持续不通过 | 测试报告 | 不交付 |

### 2.6 组织类

| # | 触发条件 | 观察方式 | 建议分级 |
|---|---|---|---|
| F1 | 客户决策人变更且未确认既有范围 | 书面确认 | 暂停 |
| F2 | 对接人失联超过 <span v-pre>{{N}}</span> 个工作日 | 沟通记录 | 暂停 |
| F3 | 我方关键人员不可用，且无法替换 | 资源记录 | 降级/暂停 |

## 三、分级与动作

| 分级 | 含义 | 动作 | 决策时限 |
|---|---|---|---|
| **观察** | 出现苗头，尚未影响交付 | 记录、加频沟通、准备预案 | 5 个工作日 |
| **降级** | 部分范围不可行 | 缩减范围、书面变更、调整价格与工期 | 3 个工作日 |
| **暂停** | 继续投入会扩大损失 | 停止新增工作、冻结代码、发书面通知、启动谈判 | 2 个工作日 |
| **终止** | 继续合作不可行 | 启动收尾流程（§五）、结算、资产处置、对外口径 | 2 个工作日 |

**升级规则**：

- 观察项 10 个工作日无改善 → 升级为降级或暂停；
- 暂停项 10 个工作日无解决 → 升级为终止；
- 任何涉及合规/安全/权利主张的触发 → 直接暂停，不等观察。

## 四、决策机制

| 项 | 必须写明 |
|---|---|
| 决策人 | <span v-pre>{{姓名/角色}}</span>，拥有暂停/终止权 |
| 知情人 | 技术负责人、商务、财务、法务 |
| 决策形式 | 书面（邮件/会议纪要），不接受口头 |
| 决策时限 | 触发后 <span v-pre>{{N}}</span> 个工作日内 |
| 记录 | 触发事实、证据、决策、理由、生效日 |
| 申诉 | 是否有复核机制，时限多久 |

**决策记录模板**：

```
止损决策记录
- 项目：
- 触发条件：（引用 §二 编号 + 事实）
- 证据：（文件/记录/日期）
- 当前分级：观察 / 降级 / 暂停 / 终止
- 决策：继续 / 降级 / 暂停 / 终止
- 理由：
- 生效日：
- 决策人：
- 知情人：
- 后续动作与责任人：
```

## 五、收尾清单

> 收尾的目标不是「结束关系」，而是**让双方都能体面地结束，并且不留下下一次的雷**。

### 5.1 资产处置

| # | 项 | 动作 | 责任人 | 完成标准 |
|---|---|---|---|---|
| 1 | 源码与分支 | 归还 / 封存 / 删除，三选一 | | 有书面确认 |
| 2 | 构建产物与镜像 | 同上 | | 有清单 |
| 3 | 账号与权限 | 移交 / 回收 / 停用 | | 有回收记录 |
| 4 | 密钥与证书 | 轮换 / 吊销 / 移交 | | 有轮换记录 |
| 5 | 数据 | 导出 / 删除 / 留存，按合同 | | 有处置证明 |
| 6 | 设备与样机 | 归还 / 折价 / 留用 | | 有签收 |
| 7 | 第三方服务 | 过户 / 停订 / 降配 | | 有账单确认 |
| 8 | 文档 | 移交 / 归档 / 销毁 | | 有目录 |

> **密钥类处置必须做**：合作终止后未轮换的密钥，是最常见的二次风险。

### 5.2 代码与文档封存

| # | 项 | 动作 |
|---|---|---|
| 1 | 打终止标签 | `tag: handover-{{YYYYMMDD}}` |
| 2 | 冻结分支 | 禁止新增提交，只允许修复 |
| 3 | 生成 as-built | 以代码为准的现状说明 |
| 4 | 生成已知问题清单 | 未关闭的 P0/P1 逐条列出 |
| 5 | 生成运行说明 | 依赖、构建、部署、回滚 |
| 6 | 生成未验证项清单 | 未做真机/压测/安全测试的部分 |
| 7 | 归档证据 | 测试报告、审查记录、决策记录 |

### 5.3 商务结算

| # | 项 | 约定 |
|---|---|---|
| 1 | 已完成工作量 | 按里程碑/人日，附证据 |
| 2 | 未完成部分 | 不计费或按比例 |
| 3 | 已发生外部成本 | 设备、账号、第三方费用 |
| 4 | 付款节点 | 收尾款的条件与时限 |
| 5 | 争议处理 | 协商 / 调解 / 仲裁，适用法律 |
| 6 | 发票与税务 | 已开票如何处理 |

### 5.4 对外口径

| # | 项 | 要求 |
|---|---|---|
| 1 | 对客户 | 书面说明终止原因、已交付内容、未完成项、后续建议 |
| 2 | 对团队 | 内部复盘，不对外传播客户信息 |
| 3 | 对潜在客户 | 不评价原客户，只讲方法与结构 |
| 4 | 公开材料 | 去标识化；不使用客户名称、品牌、截图、数据 |
| 5 | 案例化 | 只抽象方法，不复用项目内容 |

**统一口径示例**：

> 「该项目因双方在 <span v-pre>{{范围/权属/交付节奏}}</span> 上未能达成一致而终止。已完成部分按合同结算并封存。相关经验已抽象为可复用的评估方法，不涉及客户信息。」

### 5.5 团队与知识

| # | 项 | 动作 |
|---|---|---|
| 1 | 复盘会 | 事实 → 判断 → 决策 → 结果，不追责个人 |
| 2 | 经验条目 | 写入方法论或检查清单，注明来自哪次实践 |
| 3 | 模板修订 | 哪一条模板没拦住问题，改哪一条 |
| 4 | 心理收尾 | 明确「已结束」，避免长期反刍 |

## 六、收尾完成判据

全部满足才算收尾完成：

- [ ] 资产处置有书面确认；
- [ ] 密钥已轮换或吊销；
- [ ] 代码已打标签并冻结；
- [ ] as-built 与已知问题清单已交付；
- [ ] 未验证项已如实列出；
- [ ] 结算金额与付款节点已确认；
- [ ] 对外口径已统一；
- [ ] 复盘完成，至少一条经验进入模板；
- [ ] 没有未关闭的 P0 条目（或已明确承接方）。

## 七、复盘模板

```
项目复盘（止损/终止）
1. 事实时间线
   - 日期 / 事件 / 证据
2. 触发点
   - 哪个条件先出现？当时是否被识别？
3. 决策质量
   - 决策是否及时？信息是否充分？有没有更早的信号？
4. 可复用经验
   - 哪条检查清单应该新增/修改？
5. 不可复用部分
   - 哪些是本次特有，不应写入模板？
6. 下一次的前置条件
   - 哪些条件必须在签约前确认？
```

## 八、常见错误

| 错误 | 后果 | 纠正 |
|---|---|---|
| 止损条件写成感受 | 无法触发 | 改为可观察事实 + 时限 |
| 没有决策人 | 执行者硬扛 | 指定唯一决策人 |
| 暂停但不发书面通知 | 对方继续催交付 | 书面通知 + 生效日 |
| 终止但不轮换密钥 | 二次风险 | 密钥处置列为必做项 |
| 收尾不写未验证项 | 后续被追责 | 如实列出 |
| 复盘变成追责 | 没人说真话 | 对事不对人 |
| 案例化直接复用项目内容 | 侵权/违约 | 只抽象结构，去标识化 |

## 九、一页速查

```
【开始前】
□ 触发条件已写（资产/授权/需求/商务/技术/组织）
□ 决策人已指定
□ 收尾预案已确认
□ 合同含暂停/终止/结算条款

【触发时】
□ 记录事实与证据
□ 判定分级（观察/降级/暂停/终止）
□ 书面通知 + 生效日
□ 冻结新增工作

【收尾时】
□ 资产处置（源码/账号/密钥/数据/设备）
□ 代码打标签 + as-built + 已知问题
□ 结算与付款
□ 对外口径统一
□ 复盘 + 模板修订
```
