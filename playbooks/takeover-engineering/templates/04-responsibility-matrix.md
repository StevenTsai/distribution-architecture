# 模板 04｜软硬件职责边界矩阵

> **阶段**：划界 ｜ **用途**：在签约与开工前，把「谁负责什么、谁的数据算数、软件明确不做什么」写成可签字的矩阵 ｜ **版本**：v0.1
> **原则**：边界不是描述分工，而是**提前分配事故责任**。凡是出事时可能争论的地方，都必须有一行。

---

## 一、为什么需要这张表

软硬一体项目的事故，通常不发生在「功能没做」，而发生在**同一个现象有三种解释**：

- 软件说「设备没上报」；
- 固件说「软件发了非法指令」；
- 硬件说「现场干扰/供电异常」。

没有边界矩阵时，争论会退化为「谁在现场谁背锅」。有矩阵时，先查数据权威源，再查责任行。

**这张表的三个用途**：

1. **签约附件**：明确范围与除外责任；
2. **开发依据**：确定哪些逻辑必须放在哪一端；
3. **事故取证**：确定先看谁的数据、由谁出具结论。

---

## 二、责任角色定义

> 角色按「实际承担者」填，不按公司名填。一个角色可以由多方共同承担，但必须指定**唯一主责**。

| 代号 | 角色 | 典型承担方 |
|---|---|---|
| **S** | 软件（前端/小程序/App/后端） | 我方 |
| **F** | 固件/嵌入式 | 客户或第三方 |
| **H** | 硬件（板卡/传感器/执行器） | 客户或第三方 |
| **C** | 云平台/第三方服务 | 第三方 |
| **P** | 平台方（应用商店/小程序平台/运营商） | 第三方 |
| **U** | 用户/现场人员 | 客户 |
| **V** | 供应商/集成商 | 第三方 |

**主责（R）与配合（C）必须分开**：`R` 只有一个人/方；`C` 可以多个。

---

## 三、矩阵主体

> 每一行是一个**可能产生争议的能力或事件**。列填写：主责、配合、数据权威源、判定依据、兜底行为。

### 3.1 数据与状态

| # | 能力/事件 | 主责 | 配合 | 数据权威源 | 判定依据 | 软件兜底行为 |
|---|---|---|---|---|---|---|
| D1 | 设备在线/离线判定 | F | S,C | 设备心跳 | 心跳超时阈值 | 显示「未知」而非「离线」 |
| D2 | 实时值（电压/电流/温度等） | F | H,S | 设备上报 | 时间戳 + 序列号 | 超时置灰，保留最后值并标注时间 |
| D3 | 累计量/统计值 | S | F | **以哪端计算为准？** | 对账规则 | 展示口径说明 |
| D4 | 告警产生 | F | H,S | 设备侧判定 | 阈值与去抖规则 | 仅展示，不自行升级为告警 |
| D5 | 告警解除 | F | S,U | 设备侧恢复 | 恢复条件 | 不自动清除，需确认 |
| D6 | 设备时间 | F | C,S | 设备 RTC / 云端授时 | 偏差阈值 | 展示偏差，不静默纠正 |
| D7 | 用户资料/配置 | S | C | 云端数据库 | 写入审计 | 本地缓存只读 |
| D8 | 历史曲线 | S | F,C | 云端存储 | 采样与聚合规则 | 标注「采样值，非全量」 |

> **D3 是最容易出事的一行**：两端各算一套，数字对不上时无法判定谁错。必须在签约前指定唯一权威源。

### 3.2 控制与指令

| # | 能力/事件 | 主责 | 配合 | 指令发起方 | 执行方 | 失败/超时行为 |
|---|---|---|---|---|---|---|
| C1 | 远程开关/使能 | S | F,H | 软件 | 固件 | 超时回读实际状态，不假设成功 |
| C2 | 参数下发 | S | F | 软件 | 固件 | 校验回执；失败回滚显示 |
| C3 | 固件升级（OTA） | F | S,C | 软件触发 | 固件校验与写入 | 断电/断网可恢复；失败可回滚 |
| C4 | 恢复出厂 | S | F | 软件 | 固件 | 二次确认 + 结果回读 |
| C5 | 本地手动操作 | H/U | F | 现场 | 硬件/固件 | 软件只展示，不拦截 |
| C6 | 安全相关动作 | **H/F** | S | 现场或固件 | 硬件保护 | **软件不得作为唯一安全装置** |

> **C6 是红线**：如果软件参与安全链，必须单独评审，并在合同中明确「软件不承担安全认证责任」或「需另行认证」。

### 3.3 通信与协议

| # | 项 | 主责 | 配合 | 约定 |
|---|---|---|---|---|
| P1 | 通信协议定义 | F | S | 版本号、帧格式、超时、重试、校验 |
| P2 | 协议变更 | F | S | 变更通知提前期、兼容策略、回归范围 |
| P3 | 多品牌/多型号适配 | S | F,V | 适配层归属、品牌清单、差异表 |
| P4 | 网关/中继 | V | S,F | 透传或解析、故障归属 |
| P5 | 信号干扰/距离/环境 | H | U | 安装条件、免责范围 |
| P6 | 时钟同步 | F | C | 授时源与偏差容忍 |

> **协议变更必须走变更记录**：口头通知不算。变更未同步导致的联调失败，责任归发起方。

### 3.4 平台与外部依赖

| # | 项 | 主责 | 配合 | 平台限制 | 应对 |
|---|---|---|---|---|---|
| X1 | 小程序/App 审核 | S | P | 类目、资质、内容规则 | 预留审核周期；被拒不算软件缺陷 |
| X2 | 后台运行/定位/蓝牙权限 | P | S,U | 系统限制 | 明示能力边界，不承诺「一直在线」 |
| X3 | 推送到达率 | C | S | 厂商通道限制 | 不承诺 100% 到达 |
| X4 | 第三方接口可用性 | C | S | SLA、配额、计费 | 降级方案与告知 |
| X5 | 域名/证书/备案 | S | C | 合规要求 | 提前办理，不列入开发工期 |

### 3.5 安全与合规

| # | 项 | 主责 | 配合 | 约定 |
|---|---|---|---|---|
| S1 | 传输加密 | S | F | 算法、密钥协商、证书 |
| S2 | 密钥保管与轮换 | S | C | 托管位置、轮换周期、泄露处置 |
| S3 | 设备身份与绑定 | F | S | 唯一标识、防克隆、解绑规则 |
| S4 | 个人信息处理 | S | U,C | 收集范围、告知同意、留存期限 |
| S5 | 日志与审计 | S | C | 留存期限、可导出、不可篡改 |
| S6 | 漏洞响应 | S | F,H | 报告渠道、响应时限、修复责任 |

### 3.6 事故与运维

| # | 事件 | 第一响应 | 取证责任 | 判定责任 | 费用承担 |
|---|---|---|---|---|---|
| I1 | 数据异常/丢失 | S | S | 双方 | 按根因 |
| I2 | 设备损坏 | H/F | H | 第三方鉴定 | 按鉴定 |
| I3 | 误操作导致损失 | U | S | 双方 | 按合同 |
| I4 | 安全事件 | S | S | 双方 | 按根因 |
| I5 | 平台下架/封禁 | S | S | P | 按平台规则 |
| I6 | 第三方服务中断 | C | S | C | 按 SLA |

> **取证责任**：谁保管日志、谁能在多长时间内提供、日志留存多久。没有日志就没有责任判定。

## 四、安全边界声明（必填）

> 这一节必须原文进入合同附件，不能只放在技术文档里。

```
一、软件定位
本软件为「状态展示与操作辅助工具」，不构成独立的设备安全保护装置，
不替代硬件保护、固件保护或现场安全规程。

二、不承诺事项
1. 不承诺网络、平台、设备始终在线；
2. 不承诺告警在任意网络条件下实时到达；
3. 不承诺软件动作先于硬件保护生效；
4. 不承诺第三方平台规则变化后的持续可用；
5. 不承诺未经真机验证的场景。

三、用户责任
1. 按安装与使用说明操作；
2. 不绕过硬件保护；
3. 发现异常时以现场处置为先，不以软件状态为唯一依据。

四、事故处理
发生事故时，双方应在 {{N}} 小时内封存日志与设备状态，
由 {{指定方}} 出具数据，由 {{指定方}} 组织鉴定，费用按 {{规则}} 承担。
```

## 五、数据权威源确认表

> 每个关键数据只能有一个权威源。多源并存时，必须写明「以谁为准、冲突时如何处理」。

| 数据 | 权威源 | 次要来源 | 冲突处理 | 确认人 |
|---|---|---|---|---|
| 设备在线状态 | | | | |
| 实时测量值 | | | | |
| 累计量/统计 | | | | |
| 告警状态 | | | | |
| 设备配置 | | | | |
| 用户资料 | | | | |
| 固件版本 | | | | |
| 操作日志 | | | | |

**冲突处理三选一**：

- `以权威源为准，次要来源仅展示`；
- `以时间戳最新为准，并记录冲突`；
- `以人工确认为准，系统进入待确认状态`。

## 六、前置条件清单

> 这些条件不满足时，软件无法验证、无法交付或无法定责。必须写入合同前置条件。

| # | 前置条件 | 提供方 | 时限 | 未满足的后果 |
|---|---|---|---|---|
| 1 | 协议文档（含版本与变更机制） | F | | 无法联调，工期顺延 |
| 2 | 可用样机（覆盖主要型号） | H/F | | 只能仿真，真机风险自担 |
| 3 | 测试环境与账号 | C | | 无法验证 |
| 4 | 设备唯一标识规则 | F | | 无法做绑定与防重 |
| 5 | 平台资质与类目 | P/U | | 无法发布 |
| 6 | 现场安装条件说明 | H/U | | 信号问题无法定责 |
| 7 | 事故联系人名单 | 双方 | | 响应超时 |
| 8 | 数据合规要求 | U | | 不能上线 |

## 七、边界评审流程

```
草稿（我方）
   ↓
技术对齐（S × F × H）
   ↓
商务对齐（范围 × 除外责任 × 费用）
   ↓
客户确认（书面签字/邮件）
   ↓
作为合同附件冻结
   ↓
变更走变更记录（版本号 + 生效日 + 影响范围）
```

**评审时必须逐行问三个问题**：

1. 这一行出事时，先看谁的数据？
2. 这一行如果对方不配合，我方能否独立完成？
3. 这一行的责任，合同里有没有对应条款？

## 八、示例（泛化）

> 结构示例，不对应任何真实项目。

| # | 能力/事件 | 主责 | 配合 | 数据权威源 | 软件兜底 |
|---|---|---|---|---|---|
| D2 | 实时值展示 | 固件 | 硬件、软件 | 设备上报 | 超时置灰并标注最后更新时间 |
| C1 | 远程使能 | 软件 | 固件 | 设备回读 | 超时回读实际状态，不显示「成功」 |
| C3 | 固件升级 | 固件 | 软件、云 | 设备版本号 | 失败可回滚，断网可续传 |
| C6 | 过流保护 | 硬件 | 固件 | 硬件保护动作 | 软件仅展示，不作为保护手段 |
| P3 | 多品牌适配 | 软件 | 固件、供应商 | 品牌差异表 | 适配层隔离，未知型号降级为只读 |
| X1 | 平台审核 | 软件 | 平台 | 平台规则 | 预留周期，被拒不视为缺陷 |

## 九、质量检查清单

- [ ] 每个可能争议的能力都有对应行；
- [ ] 每行都有唯一主责（R），没有「共同负责」；
- [ ] 每个关键数据都有唯一权威源；
- [ ] 安全边界声明可直接作为合同附件；
- [ ] 前置条件都有提供方、时限与后果；
- [ ] 协议变更机制写明提前期与回归范围；
- [ ] 事故处理写明响应时限、取证责任与费用规则；
- [ ] 矩阵有版本号、生效日与双方签字；
- [ ] 未确认行在台账中有对应 P0/P1 条目。

## 十、常见错误

| 错误 | 后果 | 纠正 |
|---|---|---|
| 用「共同负责」代替主责 | 出事无人拍板 | 每行只留一个 R |
| 只写软件范围，不写除外责任 | 被要求兜底 | 单列「不承诺事项」 |
| 数据双源且不指定权威 | 数字对不上 | 权威源表 + 冲突处理 |
| 把软件写进安全链 | 承担无法承担的责任 | 安全边界声明 + 单独评审 |
| 协议变更靠口头 | 联调失败扯皮 | 变更记录 + 提前期 |
| 前置条件不写后果 | 工期无限顺延 | 每条写「未满足的后果」 |
| 矩阵不签字 | 只能当技术文档 | 作为合同附件冻结 |
