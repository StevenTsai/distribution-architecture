# 模板 10｜文档体系模板

> **阶段**：全阶段 ｜ **用途**：让文档「找得到、看得懂、信得过、追得回」，而不是越写越多、越写越旧 ｜ **版本**：v0.2
> **原则**：**文档不是项目的纪念品，是决策与交付的证据。**

---

## 一、文档体系的目标

接手项目最怕三种文档：

1. **找不到**——不知道哪份是最新、哪份能签；
2. **信不过**——文档写 A，代码做 B；
3. **追不回**——改了没说，出了问题无法定位。

对应三个机制：**编号与索引、状态与版本、变更与归档。**

---

## 二、文档分类

| 类别 | 回答什么问题 | 典型文档 | 主要读者 |
|---|---|---|---|
| 需求 | 做什么、为什么 | 需求说明、验收标准、范围清单 | 客户 + 团队 |
| 设计 | 怎么做 | 架构、详细设计、接口契约、数据模型 | 开发 + 测试 |
| 决策 | 为什么这样选 | ADR、方案对比、风险评估 | 团队 + 决策者 |
| 现状 | 现在是什么样 | as-built、已知问题、技术债 | 交接 + 维护 |
| 计划 | 什么时候做 | 排期、里程碑、资源计划 | 客户 + 团队 |
| 质量 | 做得对不对 | 测试报告、审查台账、验收单 | 客户 + 团队 |
| 运维 | 怎么跑、怎么救 | 部署、回滚、监控、事故手册 | 运维 + 值班 |
| 商务 | 钱与责任 | 报价、合同、变更单、结算 | 商务 + 客户 |

## 三、编号规则

```
{{项目代号}}-{{类型}}-{{YYYYMMDD}}-{{序号}}
```

| 段 | 说明 | 示例 |
|---|---|---|
| 项目代号 | 2–4 位，内部使用 | `ABC` |
| 类型 | 见下表 | `TD` |
| 日期 | 内容定稿日，不是创建日 | `20261018` |
| 序号 | 同日同类型递增 | `01` |

| 类型码 | 含义 |
|---|---|
| `RQ` | 需求 |
| `AD` | 架构 / 设计 |
| `IF` | 接口契约 |
| `DM` | 数据模型 |
| `ADR` | 决策记录 |
| `TD` | 技术设计 |
| `TS` | 测试 |
| `QA` | 质量审查 |
| `OP` | 运维 |
| `BS` | 商务 |
| `CL` | 收尾 / 归档 |
| `AS` | as-built |

**纪律**：

- 编号唯一，不复用；
- 日期是**内容日期**，不是文件创建日期；
- 文件名与编号一致，避免「最终版」「最终版2」；
- 同一文档的新版本沿用编号，版本号递增。

## 四、状态标记

每份文档头部必须有状态块：

```
状态：草稿 / 评审中 / 生效 / 已取代 / 已归档 / 冻结
版本：v{{X.Y}}
日期：{{YYYY-MM-DD}}
替代：{{被哪份文档取代}}（如适用）
依据：{{依据的代码基线 / 合同版本}}
```

| 状态 | 含义 | 可否引用 | 可否签字 |
|---|---|---|---|
| 草稿 | 内部讨论 | 否 | 否 |
| 评审中 | 待确认 | 仅内部 | 否 |
| 生效 | 已确认 | 是 | 是 |
| 已取代 | 有新版本 | 否（仅追溯） | 否 |
| 已归档 | 历史留痕 | 否 | 否 |
| 冻结 | 不再修改 | 是 | 是（作为基线） |

**硬规则**：

- 没有状态块的文档，不得作为交付物；
- 「已取代」文档必须保留，不得删除；
- 冻结文档的修改必须新开版本，不得就地改。

---

## 五、版本规则

```
主版本 vX：范围、结论、合同口径变化
次版本 vX.Y：内容补充、细节修正、笔误
```

| 变更 | 版本 | 是否需重新确认 |
|---|---|---|
| 结论变化 | 主版本 | 是 |
| 范围变化 | 主版本 | 是 |
| 新增章节 | 次版本 | 视情况 |
| 修正错误 | 次版本 | 否，但需记录 |
| 格式调整 | 不变 | 否 |

**版本记录模板**：

| 版本 | 日期 | 变更 | 变更人 | 影响 |
|---|---|---|---|---|
| v1.0 | | 初稿 | | |
| v1.1 | | 补充 §3 | | |
| v2.0 | | 范围调整 | | 需重新报价 |

## 六、文档类型模板

### 6.1 需求说明

```
1. 背景与目标
2. 范围（含/不含）
3. 用户与场景
4. 功能需求（FR-xx）
5. 业务规则（BR-xx）
6. 非功能需求（NFR-xx）
7. 验收标准（AC-xx）
8. 假设与依赖
9. 待确认项
```

### 6.2 架构设计

```
1. 目标与约束
2. 系统上下文
3. 组件与职责
4. 数据流
5. 接口与技术选型
6. 部署拓扑
7. 失败与降级
8. 安全边界
9. ADR 索引
10. 已知限制
```

### 6.3 ADR（架构决策记录）

```
ADR-{{NNN}}：{{决策标题}}
状态：提议 / 接受 / 取代 / 废弃
背景：
选项：
决策：
理由：
代价：
影响范围：
```

### 6.4 as-built

```
1. 文档定位（以代码为唯一事实源）
2. 代码基线（提交号 / 版本）
3. 实际架构
4. 实际接口
5. 实际数据模型
6. 与设计的差异
7. 已知问题
8. 技术债
9. 未验证项
```

**as-built 的三条纪律**：

1. 以代码为准，不以设计稿为准；
2. 差异必须列出，不粉饰；
3. 未验证项必须写，不省略。

### 6.5 测试报告

```
1. 范围与环境
2. 测试套件与用例数
3. 通过 / 失败 / 跳过
4. 失败分析
5. 未覆盖项
6. 结论
```

### 6.6 事故手册

```
1. 事故分级
2. 发现与上报
3. 止血动作
4. 取证与封存
5. 恢复步骤
6. 对外沟通
7. 复盘要求
```

## 七、目录结构

```
doc/
├── 00-索引.md              # 全量文档索引与状态
├── 需求/
│   ├── md/
│   └── pdf/
├── 设计/
│   ├── md/
│   └── pdf/
├── 契约/
├── 决策/
├── 质量/
├── 运维/
├── 商务/
├── 归档/
└── 接手工程/               # 方法论与模板
```

**规则**：

- 目录按「类别」分，不按「人」分；
- md 是源文件，pdf/docx 是交付物；
- 归档目录只增不改；
- 每层有 `README.md` 或索引。

---

## 八、索引

`doc/00-索引.md` 必须包含：

| 编号 | 文档 | 版本 | 状态 | 日期 | 读者 | 说明 |
|---|---|---|---|---|---|---|
| | | | | | | |

**索引维护规则**：

1. 新文档创建时立即登记；
2. 状态变化时更新；
3. 被取代时标注替代关系；
4. 每月核对一次「索引 vs 实际文件」；
5. 索引本身也有版本与状态。

## 九、变更与归档

### 9.1 变更流程

```
提出变更
  ↓
判断影响（结论/范围/仅细节）
  ↓
升版本
  ↓
更新变更记录
  ↓
更新索引
  ↓
旧版本归档（不删除）
```

### 9.2 归档规则

| 场景 | 动作 |
|---|---|
| 新版本生效 | 旧版本移入 `归档/`，保留编号 |
| 项目终止 | 全量打标签，生成收尾索引 |
| 合同签署 | 签署版冻结，禁止就地修改 |
| 文档废弃 | 状态改「已归档」，写明原因 |

## 十、质量检查清单

- [ ] 每份文档有编号、版本、状态、日期；
- [ ] 编号规则统一，无重号；
- [ ] 索引与实际文件一致；
- [ ] 生效文档有确认人；
- [ ] 被取代文档保留并可追溯；
- [ ] as-built 以代码为基线，差异与未验证项齐全；
- [ ] 合同/报价类文档有有效期与适用版本；
- [ ] 归档目录只增不改；
- [ ] 交付包有清单与校验方式；
- [ ] 敏感信息未进入公开文档。

---

## 十一、常见错误

| 错误 | 后果 | 纠正 |
|---|---|---|
| 文件名写「最终版」 | 无法判断谁最新 | 编号 + 版本 |
| 文档无状态 | 草稿被当成承诺 | 状态块 |
| 就地改签署版 | 失去合同证据 | 冻结 + 新版本 |
| 删除旧版本 | 无法追溯 | 归档 |
| 索引不更新 | 找不到文档 | 创建即登记 |
| as-built 抄设计稿 | 交接被误导 | 以代码为准 |
| 文档写满客户信息 | 泄露风险 | 去标识化 |
| 只写结论不写依据 | 无法复核 | 附证据与假设 |
