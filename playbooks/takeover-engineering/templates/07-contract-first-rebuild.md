# 模板 07｜契约优先重建方案

> **阶段**：重建 ｜ **用途**：在存量系统上重建或替换一部分能力时，先冻结契约，再写实现，最后用两端夹逼证明 ｜ **版本**：v0.2
> **前置**：已完成 `templates/04-responsibility-matrix.md`，且关键接口有证据等级。

---

## 一、为什么契约优先

接手项目最常见的返工不是「写错代码」，而是**三方对同一个字段有三种理解**：

- 客户端按旧行为消费；
- 文档按新设计描述；
- 新实现按「更合理」的方式写。

结果：单元测试全绿，联调全红。

**契约优先的含义**：

1. 契约以**真实消费方**的行为为准，不以文档为准；
2. 契约先冻结、再实现；
3. 实现必须能指出「哪一行对应契约的哪一条」；
4. 任何契约变更都走变更记录，不允许静默「优化」。

---

## 二、契约来源与证据

| 来源 | 证据等级 | 可信度 | 使用方式 |
|---|---|---|---|
| 客户端真实请求/响应 | E2 | 最高 | 逐字段记录，作为冻结基线 |
| 服务端源码 | E1 | 高 | 与客户端消费对照，冲突以客户端为准 |
| 接口文档/OpenAPI | E3 | 中 | 只能作为参考，需验证 |
| 旧系统行为录像/截图 | E2 | 高 | 用于状态与文案 |
| 口头说明 | E5 | 低 | 必须书面确认后才可用 |

**冲突处理顺序**：

```
真实客户端消费 > 服务端实现 > 接口文档 > 口头说明
```

冲突本身必须记入台账，不能自行选一个「看起来对的」。

### 3.1 字段级要求

| 项 | 必须写清 |
|---|---|
| 字段名 | 原样保留，不「规范化」 |
| 类型 | string / number / boolean / null，不用「字符串或数字」 |
| 可空 | 是否允许 null / 缺省 / 空串 |
| 枚举 | 全部取值与顺序，未知值的行为 |
| 精度 | 小数位、单位、缩放 |
| 时间 | 时区、格式、精度 |
| 错误 | 文案原文，不改写 |

## 四、分层标注

实现中的每个接口、每个字段、每段关键逻辑都要标注来源：

| 标注 | 含义 | 处理要求 |
|---|---|---|
| `[源码]` | 从存量源码直接还原 | 必须逐行核对 |
| `[运行]` | 通过运行/抓包确认 | 必须可复现 |
| `[推断]` | 根据命名/行为反推 | 必须写假设，联调时验证 |
| `[新建]` | 存量没有，按需求新增 | 必须有验收标准 |

**纪律**：

- `[推断]` 不得直接进入验收承诺；
- `[新建]` 必须单独列范围与工作量；
- 标注要跟着代码走，不能只写在文档里。

## 五、失败矩阵

> 成功路径决定能不能演示，失败路径决定能不能上线。

每个接口至少覆盖以下维度：

| 维度 | 要回答的问题 | 期望行为 |
|---|---|---|
| 超时 | 多久算超时 | 返回什么、是否重试 |
| 重试 | 重试几次、间隔多少 | 是否幂等 |
| 网络中断 | 请求发出但无响应 | 客户端如何恢复 |
| 部分失败 | 批量中部分成功 | 返回结构、补偿方式 |
| 重复请求 | 同一请求发两次 | 幂等键 / 去重 |
| 并发 | 两个客户端同时改 | 乐观锁 / 后写覆盖 |
| 权限失效 | token 过期/被吊销 | 401 语义、跳转 |
| 降级 | 依赖不可用 | 缓存 / 默认值 / 明确报错 |
| 数据异常 | 缺字段、类型错、超范围 | 拒绝还是兜底 |
| 时钟偏差 | 两端时间不一致 | 以谁为准 |

### 5.1 失败矩阵模板

| 接口 | 场景 | 触发方式 | 期望 | 实际 | 测试 |
|---|---|---|---|---|---|
| API-001 | 超时 | | | | |
| API-001 | 重复提交 | | | | |
| API-001 | 权限失效 | | | | |

## 六、适配层隔离

> 目标：**没有硬件、没有后端、没有第三方账号，也能开发与演示。**

```
页面 / 业务逻辑
      │
      ▼
适配层（统一接口）
      │
 ┌────┼────────────┬─────────────┐
 ▼    ▼            ▼             ▼
mock  sim         real        replay
静态  模拟协议栈   真实设备/后端   录制回放
```

### 6.1 适配层规则

1. 页面只调用适配层，不直接调用平台 API；
2. 适配层接口一旦冻结，三种模式行为必须一致；
3. mock/sim 的返回值必须来自契约卡，不得自造字段；
4. real 模式的失败必须能在 sim 中复现；
5. 切换模式只改配置，不改业务代码。

### 6.2 模式矩阵

| 能力 | mock | sim | real | replay |
|---|---|---|---|---|
| 无网络运行 | ✅ | ✅ | ❌ | ✅ |
| 真实协议帧 | ❌ | ✅ | ✅ | ✅ |
| 真实硬件 | ❌ | ❌ | ✅ | ❌ |
| 可重复 | ✅ | ✅ | ❌ | ✅ |
| 演示友好 | ✅ | ✅ | 需设备 | ✅ |

## 七、两端夹逼验证

### 7.1 基本形态

```
真实客户端 ──契约──> 真实服务端
     │                    │
     └── 任一端违约，测试变红 ──┘
```

**不要**只做：

- 真实客户端 × Mock 后端（只证明客户端自洽）；
- Mock 客户端 × 真实后端（只证明后端自洽）。

### 7.2 测试清单

| 测试 | 证明什么 | 失败时指向 |
|---|---|---|
| 客户端契约测试 | 客户端按契约发请求 | 客户端 |
| 服务端契约测试 | 服务端按契约响应 | 服务端 |
| 端到端测试 | 主链路可用 | 链路 |
| 对拍测试 | 独立实现一致 | 算法/实现 |
| 回归测试 | 旧行为未被破坏 | 变更点 |

### 7.3 对拍（独立第二实现）

适用场景：加密、编码、校验、算法、协议解析。

规则：

1. 用不同语言/框架实现同一逻辑；
2. 输入样本覆盖边界与异常；
3. 逐位/逐字节比较，不做「近似相等」；
4. 基准实现应是**仓外可验证**的（标准库、官方实现、真机）；
5. 对拍不过时，先确认基准，再改实现。

## 八、契约变更流程

```
提出变更
  ↓
影响分析（客户端/服务端/数据/测试）
  ↓
变更单（范围 + 工作量 + 兼容策略）
  ↓
双方确认
  ↓
更新契约卡（版本号 + 生效日）
  ↓
更新实现与测试
  ↓
回归
```

**变更单必须写**：

- 变更前后字段对照；
- 旧客户端是否兼容；
- 数据是否需要迁移；
- 测试需要新增/修改哪些；
- 对工期与价格的影响。

**禁止**：

- 口头变更；
- 在代码里「先兼容一下」但不更新契约；
- 删除旧字段但不通知消费方。

## 九、as-built 对照

重建完成后，必须产出「实现 vs 契约」对照：

| 契约项 | 实现位置 | 状态 | 未实现原因 | 验证方式 |
|---|---|---|---|---|
| API-001 | `src/...` | ✅ | | 契约测试 |
| API-002 | `src/...` | 🟡 | 第三方未开通 | 手工验证 |
| API-003 | — | ⏳ | 范围外 | — |

**状态定义**：

- ✅ 已实现并验证；
- 🟡 已实现未完全验证；
- ⏳ 未实现（必须写原因）；
- ❌ 明确不做（必须写依据）。

## 十、质量检查清单

- [ ] 每个接口都有契约卡；
- [ ] 契约卡以真实消费方为准；
- [ ] 每个字段都有类型、可空、枚举、精度；
- [ ] 错误文案原样保留；
- [ ] 每个接口都有失败矩阵；
- [ ] 适配层三种模式行为一致；
- [ ] 契约测试能指出是哪一端违约；
- [ ] 关键算法有独立对拍；
- [ ] 契约变更走变更单；
- [ ] as-built 对照无断点，未实现项如实标注。

## 十一、常见错误

| 错误 | 后果 | 纠正 |
|---|---|---|
| 按文档实现 | 与真实客户端不兼容 | 以客户端消费为准 |
| 顺手「优化」字段名 | 旧客户端解析失败 | 字段名原样保留 |
| 枚举顺序改变 | 按索引取值的客户端错乱 | 枚举顺序冻结 |
| 只测成功路径 | 上线后异常态崩溃 | 失败矩阵 |
| 用 Mock 代替真实联调 | 两端都自洽，合起来不通 | 两端夹逼 |
| 对拍用近似比较 | 加密/校验错位未发现 | 逐位比较 |
| 变更不更新契约 | 文档与实现再次分叉 | 变更单 + 版本号 |
| as-built 只写「已完成」 | 未验证项被掩盖 | 四态标注 |
