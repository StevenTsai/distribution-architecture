# 模板 09｜质量审查台账

> **阶段**：证明 ｜ **用途**：把多轮审查的「发现 → 修复 → 回归 → 关闭」变成可追溯记录，而不是一次性口头结论 ｜ **版本**：v0.2
> **原则**：**审查的价值不在发现数量，而在关闭质量与回归证据。**

---

## 一、审查类型

| 类型 | 看什么 | 适用阶段 | 产出 |
|---|---|---|---|
| 静态审查 | 结构、命名、复杂度、死代码、硬编码 | 接手初期 / 每次提交 | 发现清单 |
| 契约审查 | 字段、错误码、枚举、幂等 | 联调前 | 契约差异 |
| 安全审查 | 认证、授权、输入校验、密钥、日志 | 上线前 / 变更后 | 风险清单 |
| 数据审查 | 口径、精度、时区、迁移、合规 | 数据相关变更 | 数据问题 |
| 体验审查 | 状态覆盖、异常文案、空态、可恢复性 | 验收前 | 体验问题 |
| 回归审查 | 旧行为是否被破坏 | 每次修复后 | 回归结果 |

---

## 二、发现字段

| 字段 | 必填 | 说明 |
|---|---|---|
| ID | ✅ | `F-{{轮次}}-{{序号}}`，如 `F-R1-01` |
| 轮次 | ✅ | R1 / R2 / … |
| 类型 | ✅ | 上表六类 |
| 标题 | ✅ | 一句话说清缺陷 |
| 位置 | ✅ | `file:line` / 接口 / 文档章节 |
| 严重度 | ✅ | Critical / High / Medium / Low |
| 描述 | ✅ | 触发条件 + 实际行为 + 期望行为 |
| 影响 | ✅ | 功能、安全、数据、责任 |
| 证据 | ✅ | 复现步骤 / 日志 / 抓包 |
| 根因 | ✅ | 不是「忘了」，而是机制缺失 |
| 修复方案 | ✅ | 具体动作 |
| 回归用例 | ✅ | 测试名，失败即阻断 |
| 责任人 | ✅ | 一人 |
| 状态 | ✅ | 打开 / 修复中 / 待验证 / 已关闭 / 不修（附理由） |
| 关闭证据 | ✅ | 提交号 / 测试报告 |

---

## 三、严重度定义

| 级别 | 判定 | 处理要求 |
|---|---|---|
| **Critical** | 数据丢失、安全漏洞、资金错误、无法启动 | 立即修，未关闭不得交付 |
| **High** | 主链路不可用、契约不兼容、责任边界缺失 | 本轮修复，未关闭不得验收 |
| **Medium** | 异常态缺失、性能明显下降、可维护性风险 | 排期修复，可带条件交付 |
| **Low** | 命名、注释、轻微体验问题 | 可进入技术债 |

**升级规则**：

- 同一根因出现 3 次以上 → 升级为机制问题，改流程/模板；
- Critical/High 修复后引入新问题 → 本轮审查不通过，重新开轮；
- 「不修」必须有书面理由与承接方。

---

## 四、轮次结构

```
R1 全量审查（基线）
   ↓ 修复
R2 复审（验证修复 + 抽查未改区域）
   ↓ 修复
R3 专项审查（安全/契约/数据）
   ↓ 修复
R4 回归审查（全量回归 + 守护测试）
   ↓
关闭
```

每轮记录：

| 轮次 | 日期 | 范围 | 审查人 | 发现数 | Critical | High | 已关闭 | 未关闭 | 结论 |
|---|---|---|---:|---:|---:|---:|---:|---|
| R1 | | | | | | | | | |
| R2 | | | | | | | | | |

**独立性要求**：

- 修复者不得单独关闭自己的发现；
- 审查人应尽量独立于实现者；
- 无法独立时，至少做交叉复核并记录。

## 六、关闭标准

一条发现只有满足以下条件才能关闭：

1. **修复已合入**：有提交号或变更记录；
2. **回归已运行**：测试通过，且测试覆盖触发条件；
3. **未引入新问题**：相关区域回归通过；
4. **证据可追溯**：提交 + 测试报告 + 复现记录；
5. **非自证**：修复者以外的人确认（至少抽查）。

**不算关闭**：

- 「已改」但无测试；
- 「测试过了」但测的不是触发条件；
- 「下版本修」但无新条目承接；
- 「客户接受」但无书面记录。

## 七、指标

| 指标 | 计算 | 用途 |
|---|---|---|
| 发现密度 | 发现数 / 千行代码 | 判断代码质量 |
| Critical/High 占比 | 高严重度 / 总发现 | 判断风险 |
| 关闭率 | 已关闭 / 总发现 | 判断执行 |
| 平均关闭时长 | Σ关闭时长 / 关闭数 | 判断响应 |
| 回归逃逸率 | 修复后新发现 / 已关闭 | 判断修复质量 |
| 重复根因率 | 同根因发现 / 总发现 | 判断机制问题 |

**健康信号**：

- 轮次越往后，Critical/High 应显著下降；
- 回归逃逸率应趋近 0；
- 重复根因率上升时，停止逐条修，改机制。

---

## 八、守护测试

> 每个 Critical/High 发现，至少产出一条守护测试。没有守护测试的修复，会在下一次改动中静默回归。

| 发现 ID | 守护测试 | 断言什么 | 失败时提示 |
|---|---|---|---|
| F-R1-01 | `guard_auth_expiry` | 过期 token 必须 401 | 「权限失效语义被破坏」 |
| F-R1-02 | `guard_ota_hash` | 哈希不符必须拒刷 | 「OTA 校验被绕过」 |

**守护测试要求**：

1. 测试名表达「保护什么」，不是「测试什么」；
2. 失败信息直接指出红线；
3. 纳入 CI，失败即阻断；
4. 不因「太严格」而删除，只可调整实现。

## 十一、质量检查清单

- [ ] 每条发现都有 ID、位置、严重度、证据；
- [ ] 每条 Critical/High 都有根因与守护测试；
- [ ] 修复者未单独关闭自己的发现；
- [ ] 关闭有提交号与回归证据；
- [ ] 「不修」有书面理由与承接方；
- [ ] 每轮有统计与结论；
- [ ] 重复根因已触发机制改进；
- [ ] 审查范围明确（哪些没审）；
- [ ] 报告可签字。

---

## 十二、常见错误

| 错误 | 后果 | 纠正 |
|---|---|---|
| 只统计数量，不看严重度 | 用低价值发现刷指标 | 分严重度看趋势 |
| 自己修自己关 | 未验证的「已修复」 | 交叉复核 |
| 修复无回归用例 | 下次改动静默回归 | 守护测试 |
| 根因写「疏忽」 | 无法改进机制 | 写到机制层 |
| 审查范围不写 | 被误认为全量审过 | 明确「未覆盖」 |
| 为过审删测试 | 红线失守 | 只改实现，不删守护 |
| 报告只写结论 | 无法追溯 | 附发现清单与证据 |
