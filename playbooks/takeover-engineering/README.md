# 接手工程工具箱（Takeover Engineering Toolkit）

> **版本**：v0.4 ｜ **日期**：2026-10-24 ｜ **状态**：已随本仓库发布
> **定位**：把「接手一个不属于自己的系统」从个人经验，变成可复用、可交付、可定价的方法与模板。
> **来源**：抽象自一次私有的软硬一体系统评估实践（2026-09～10）。文中已去除客户名称、品牌、金额、协议细节与业务字段；相关商务合作最终未签署合同，本工具箱为独立创作的方法论，不包含任何客户交付物。

## 与本仓库的关系

本仓库的主体内容回答的是**「系统怎么建」**——设计模式、ADR、生产案例；接手工程工具箱回答的是另一半问题：**「系统怎么接手」**——该不该接、接多少、报多少钱、什么时候停。

| | 本仓库已有内容 | 本工具箱补的 |
|---|---|---|
| 关注点 | 系统怎么设计（模式/ADR） | 系统怎么接手（评估/缺口/边界） |
| 决策类型 | 技术选型怎么做对 | 商务与投入怎么做对 |
| 面向读者 | 架构师 / 开发者 | 售前 / 商务 / 决策者 |

两者合起来才是完整叙事：不光会建，还会接、会估、会止损。工具箱中的 21 问、L0–L3 投入分级、杠杆对称等方法不绑定任何技术栈。

> **姊妹篇**：[架构组合治理工具箱](../system-portfolio-governance/)——接手工程管系统进入的那一刻，组合治理管系统进入之后的整个持有期（哪些该关、哪些该治、怎么防只增不减）。两篇共享证据分级、止损前置、决策留痕三套底层思想。

### 思想同源

两边不是拼盘，几条核心原则在技术侧早有对应——同一个判断，在不同层的应用：

| 工具箱 | 本仓库技术侧 |
|---|---|
| 两端夹逼（谁不守契约谁红） | [跨语言契约测试](../../architecture/cross-language-contract-testing.md)：仓外裁判、fixture 对拍，本质同一件事 |
| 止损前置（在开始前定义结束） | [Redis 可插拔 ADR](../../decisions/why-redis-optional.md)：回切零代码，就是技术侧的退出条件 |
| 证据分级 E1–E5（结论必须附证据） | 各 ADR 的 trade-off 记录：结论附证据，不附权威 |
| 三落点（合同 / 代码 / 测试） | fail-fast 守护 + 守护测试（[生产护栏案例](../../case-studies/production-guardrails/)）：规则不靠自觉 |

## 一、它解决什么问题

接手项目的失败，通常不是技术不行，而是四件事没有在动手前说清：

1. **不知道继承了什么**——源码缺文件、构建跑不起来、文档与线上不一致；
2. **不知道还剩多少活**——把「能打开」当成「能交付」，工作量估成拍脑袋；
3. **不知道谁负责什么**——软件、固件、硬件、第三方的责任边界模糊，出事故才吵；
4. **不知道什么时候该停**——没有退出条件，越做越沉没。

这套工具箱把上述四件事拆成六个阶段、四条原则、十份可直接填写的模板，以及一份用于首次沟通的免费提问清单。

## 三、三层用法

### 第一层：免费钩子（获客）

直接使用 [21 个问题](hooks/21-questions.md)，作为首次沟通或领取联系方式的内容钩子。

**只放问题，不放答案。** 问题是你自己的方法论；答案属于具体客户。

### 第二层：付费评估（3 个工作日）

用模板 01–04 完成一次接手前评估，交付：

- 资产清单与缺口
- 复用度四分类表
- 缺口与风险台账
- 软硬件职责边界矩阵
- 增量报价建议（模板 06）

卖的是「判断」，不是「工时」。

### 第三层：交付治理（签约后）

用模板 03–05、07–10 贯穿项目：每个风险项落到合同条款、代码约束与守护测试三处；契约先冻结再实现；每个阶段保留止损闸门；验收走追溯矩阵；收尾时按模板 05 归档。

---

### 使用顺序（按六阶段）

```
接洽   01 签约前投入纪律  ← 工具箱根目录文档，与模板 01 不同
取证   模板 01 接手指南与资产清单
量化   模板 02 复用度评估表  +  模板 03 缺口与风险台账
划界   模板 04 软硬件职责边界矩阵  +  模板 03 更新
定价   模板 06 增量报价模型
重建   模板 07 契约优先重建方案
证明   模板 08 验收追溯矩阵  +  模板 09 质量审查台账
全程   模板 05 止损与收尾清单  +  模板 10 文档体系模板
获客   hooks/21 个问题
```

> 不必一次全用。第一次接触客户只用钩子；付费评估用 01–04 + 06；签约后用 03–05、07–10。顶层《01 签约前投入纪律》贯穿接洽到定价——它管的不是「怎么评估」，而是「评估期间自己能花多少」。

## 四、核心原则（摘要）

| 原则 | 一句话 | 操作化定义 |
|---|---|---|
| **证据分级** | 不把推断当事实 | 每个结论标注 E1–E5（源码 / 运行 / 文档 / 推断 / 假设） |
| **三落点** | 风险必须被三处接住 | 合同条款类别 + 代码约束 + 守护测试，缺一即未闭环 |
| **两端夹逼** | 谁不守契约谁红 | 真实客户端 × 真实服务端；独立第二实现逐位对拍 |
| **止损前置** | 在开始前定义结束 | 触发条件、决策人、时限、退出成本写进项目章程或合同 |

详细定义见 [00 方法论总纲](00-methodology.md) §三。

## 五、合规边界

本工具箱是**结构抽象**，不是项目文档的搬运。使用时遵守：

1. **只复用结构**：问题清单、分类维度、评分模型、决策规则、文档骨架；
2. **不复用内容**：客户名称、品牌、产品型号、截图、协议命令号、密钥、域名、金额、合同原文、真实业务字段；
3. **示例全部泛化**：使用「某设备管理小程序」「品牌 A」「模块 M1」等占位；
4. **对外交付前检查**：对成稿执行关键词复查（客户名、品牌、域名、appid、手机号、金额、协议号）。

本仓库版本已完成上述脱敏复核（2026-10-24）。

## 六、更新原则

本工具箱按**「实践 → 学费 → 规则」**的回路更新：先有真实经历（尤其是没做对的经历），再提炼为规则，最后才落进模板。不以营销为目的增删内容——每个拦截点背后都得真有人差点踩进去。若某条规则没有对应的学费，它就不该出现在这里。
