## 与姊妹篇的关系

三篇方法论覆盖一个系统的三种处境：

| | [接手工程](../takeover-engineering/) | [组合治理](../system-portfolio-governance/) | 本篇 |
|---|---|---|---|
| 管什么 | **进入时**：该不该接、接多少 | **持有期**：哪些该关、哪些该治 | **运行期**：怎么让它活着 |
| 核心问题 | 投入会不会打水漂 | 系统群是不是只增不减 | 出事时你能不能看见、敢不敢改、会不会救 |
| 止损思想 | 投入封顶、到期暂停 | 12 个月无发布自动复审 | 变更必须有回滚、告警必须可执行 |

## 它解决什么问题

运维事故的类型在全世界重复出现，根因高度集中：

1. **出事才知道**——没有业务指标告警，用户投诉是第一个监控；
2. **变更靠勇**——全量发布、没有灰度、回滚靠「现想」；
3. **救火靠英雄**——没有分级、没有指挥、没有沟通节奏，谁在线谁上；
4. **预案靠想象**——故障切换、容灾方案从没演练过，第一次执行就是实战。

本方法论拆成**五条原则、四个能力域、四份可直接填写的模板**，外加一篇面向平台建设的深水区附录。

## 使用节奏：按团队规模渐进

| 阶段 | 团队 | 最小动作 |
|---|---|---|
| **最小可行** | 3–10 人 | 3 条业务告警 + 变更日志 + 事故模板 + 每季度一次演练 |
| **成长期** | 10–30 人 | 全量告警规范 + 应用灰度发布 + 复盘制度 + 值班轮转 |
| **成熟期** | 30 人以上 | 演练常态化 + 容量模型 + 混沌演练 + 变更数据分析 |

> 不要按「成熟期」的标准要求小团队——**一份执行不了的全套规范，效果不如三条真正会被看见的告警**。按阶段取用。
