# 深水区：全链路灰度的实现细节

> [模板 02](../templates/02-change-and-canary.md) 回答「灰度怎么分批、怎么判停」；本篇回答更难的一半：**放量的那部分流量，怎么保证从头到尾都走新版本。**

---

## 一、全链路与非全链路

只有入口灰度的发布是这样的：

```
入口 1% → 新版本服务 A
             ↓
         服务 B（全量旧版本）
             ↓
         服务 C（全量旧版本）
```

看起来安全，实际上新版本 A 立刻接收全量真实流量，却在旧版本 B、C 上跑——**你验证的是「A 与旧 B/C 的兼容性」，不是「新版本」**。如果新逻辑依赖 B 的新字段，问题会在 1% 阶段暴露；如果不依赖，1% 阶段其实什么也没验证到。

全链路灰度要求：

```
入口 1% → A' → B' → C' → 数据（兼容新旧）
             │    │    │
          全链路标记一致，不允许中途落回旧版本
```

**核心不变量：同一请求在其完整生命周期内，版本与标记不变。**

---

## 二、三个概念，不要混用

| 概念 | 是什么 | 由谁产生 | 生命周期 |
|---|---|---|---|
| **实例标签** | 实例属于哪个版本/分组（如 `version=v2`、`group=beta`） | 部署时注入 | 实例存活期 |
| **流量标记** | 这次请求应该走哪个分组（如 `tag=beta`） | 入口网关 | 单次请求 |
| **路由规则** | 标记与标签如何匹配、匹配不到怎么办 | 治理平台统一下发 | 长期，可变更 |

常见错误是只做前两个、不做第三个的**兜底定义**——新版本实例挂了，带标记的请求是排队等、降级走旧版本、还是直接失败？这个决策必须在发布前写进发布单。

---

## 三、入口：标记怎么打

| 方式 | 适用 | 注意 |
|---|---|---|
| 白名单（用户/设备/租户） | 内部员工、种子用户 | 名单要有 owner 和有效期 |
| 请求头/参数 | 压测、联调、特定渠道 | 必须防伪造，外部请求不可信 |
| 按比例随机 | 常规放量 | **同一次用户会话要稳定**，否则来回切换会出现状态不一致 |
| 按单元/地域 | 已做单元化的系统 | 与单元路由合并计算，注意优先级 |

比例灰度的坑：每次请求独立随机，用户会在新旧版本间反复跳。正确做法是按**稳定标识哈希**取模（用户 ID、设备 ID、会话 ID），保证同一用户在一段时间内固定落在同一侧。

---

## 四、透传：标记怎么一路不丢

这是全链路灰度 80% 的工程量所在。

### 4.1 三种介质

| 介质 | 透传方式 | 易失点 |
|---|---|---|
| HTTP | 请求头（自定义 header） | 网关改写、重定向、跨域预检、第三方回调 |
| RPC | 调用上下文（attachment/context） | 序列化框架丢弃未知字段、泛化调用 |
| 消息 | 消息头/属性 | 生产者未设置、消费者反序列化丢失 |

### 4.2 五个必查的丢失点

1. **线程池与异步**：标记存在 ThreadLocal 里，提交任务时没传递，异步线程读不到；
2. **线程池复用**：上一个任务的标记残留到下一个任务，**比丢失更危险**——会污染无关请求；
3. **重试**：重试时新建了请求对象，标记没复制；
4. **定时任务与补偿**：没有入口请求，标记从哪来？必须有明确规则（通常走默认版本）；
5. **第三方回调**：外部系统不会带回你的标记，回调路径必须设计「无标记时如何路由」。

### 4.3 判断透传是否正确的指标

**标记丢失率**：进入系统时带标记的请求数 ÷ 下游收到带标记的请求数。健康值应恒为 0。

这个指标比任何架构图都直接。上线第一天就建它，否则你无法知道灰度是不是真的「全链路」。

## 五、消费端：匹配与兜底

每个服务在发起调用前做一次决策：

```
有明确标记？
  ├── 是 → 找带对应标签的实例
  │         ├── 找到 → 路由过去
  │         └── 找不到 → 按兜底策略（见下）
  └── 否 → 按默认规则（通常走稳定版本）
```

兜底策略三选一，必须显式配置：

| 策略 | 行为 | 适用 |
|---|---|---|
| **回落稳定版** | 找不到新版本就走旧版本 | 大多数业务；保证可用性优先 |
| **严格模式** | 找不到就失败/排队 | 数据不能混跑的验证场景 |
| **就近同单元** | 先按单元路由，再按版本 | 已单元化的系统 |

严格模式只应存在于验证阶段，且必须设置超时——**严格模式下的等待，就是一次人为制造的事故**。

---

## 六、消息灰度：最难的一块

同步调用可以「找不到就回落」，消息不行：消息一旦投递，消费端版本就固定了。三种方案：

### 6.1 方案 A：按版本分主题

```
业务主题-v1  ← 旧版本消费者
业务主题-v2  ← 新版本消费者
```

- 优点：隔离彻底，回滚只需停订阅；
- 代价：主题数翻倍，跨版本顺序无法保证，切换瞬间可能重复消费；
- 适用：版本差异大、消息量中等。

### 6.2 方案 B：分区绑定

生产端按「单元键/用户键」分区，新版本消费者只订阅分配给自己的分区。

- 优点：主题数不变，顺序在分区内保持；
- 代价：需要控制分区分配，扩缩容时重平衡复杂，积压时无法快速转移；
- 适用：已有分区键、消费能力可预估。

### 6.3 方案 C：消息头携带标记，消费端过滤

- 优点：实现最简单；
- 代价：过滤发生在消费端，**错误隔离最弱**——旧版本消费者仍会收到新版本消息（除非显式跳过），跳过逻辑本身也是新代码；
- 适用：验证期短、消息量小、可接受重复投递。

### 6.4 无论哪种都要回答的四个问题

1. 灰度期间积压的旧版本消息，由谁消费？
2. 回滚后，新版本已投递但未消费的消息怎么办？
3. 同一条业务消息被两个版本各消费一次，幂等是否成立？
4. 消费失败进入重试队列后，版本标记还在吗？

**四个问题有一个答不上来，就不要做消息灰度。**

## 七、数据层：最容易被忽略的版本

应用可以灰度，数据库不行。灰度期间数据层必须**双向兼容**：

- 新版本写入的字段，旧版本读到时不能报错（加字段、给默认值）；
- 旧版本写入的数据，新版本要能正确处理（兼容旧格式）；
- 不允许在灰度期间修改字段语义、删除字段、改变唯一约束。

这与 [模板 02 的 expand–contract](../templates/02-change-and-canary.md) 是同一件事：**数据库变更的时间单位是「版本窗口」，不是「一次发布」。**

缓存的额外问题：新旧版本共用缓存时，缓存键必须包含版本或数据结构标识，否则新版本写入的结构会被旧版本读出并解析失败。简单做法是**灰度期间禁用共享缓存**或**加版本前缀**。

## 八、十个常见坑

| # | 坑 | 表现 | 处理 |
|---|---|---|---|
| 1 | 线程池丢标记 | 异步链路落回旧版本 | 提交任务时显式传递上下文 |
| 2 | 线程池残留标记 | 无关请求被路由到新版本 | 任务结束清理上下文 |
| 3 | 网关剥离自定义头 | 下游全部无标记 | 网关白名单放行并加测试 |
| 4 | 重试丢标记 | 重试请求走旧版本 | 重试构造时复制上下文 |
| 5 | 定时任务无标记 | 批处理落在哪边不确定 | 显式配置默认分组 |
| 6 | 第三方回调无标记 | 回调走旧版本，状态不一致 | 回调按业务键路由 |
| 7 | 缓存跨版本污染 | 反序列化失败或脏读 | 缓存键加版本前缀 |
| 8 | 消息重复消费 | 灰度切换瞬间重复处理 | 幂等键 + 去重表 |
| 9 | 双重路由 | 入口与单元路由冲突 | 明确优先级：单元 > 版本 > 默认 |
| 10 | 观察窗口太短 | 低频问题没暴露就全量 | 按业务周期定窗口，不按心情 |

## 九、流水线与自动化判停

灰度不应依赖人盯屏幕：

```
构建 → 部署 beta 实例 → 打标 → 入口 1%
  → 自动校验（错误率/P99/业务指标 vs 基线）
  → 5% → 25% → 50% → 100%
  → 每步失败自动回滚并通知
```

三个自动化要点：

- **基线要动态**：与「同时段上周」比较，而不是固定阈值；
- **判停要有滞后保护**：连续 N 个采样周期超标才停，避免抖动误杀；
- **回滚要快于告警**：判停触发后直接执行回滚，而不是先通知人确认。

## 十、小团队的最小可行版本

全链路灰度是平台能力，小团队做不到全部。按投入产出排序，先做四件事：

1. **入口按用户哈希分流**（10% 固定用户），不做链路透传——至少验证了入口与新版本本身；
2. **关键链路透传一个 header**，先覆盖「入口 → 核心服务 → 核心依赖」三跳；
3. **发布单写清兜底策略**：找不到新版本实例时怎么办；
4. **每次灰度记录一次「标记丢失率」**，哪怕手工统计。

这四件事的成本约等于一次发布多花半天，能挡住大部分「灰度了但没验证到」的假安全。

---

## 十一、诚实边界

- 本篇讲机制与判断，不绑定具体网关、注册中心、消息中间件；
- 方案 A/B/C 的适用性随消息量与消费模式变化，需要按系统实测；
- 全链路灰度无法覆盖「数据不可逆变更」——那类变更只能靠 expand–contract 和备份，不靠灰度；
- 灰度降低的是**影响面**，不降低**变更频率**；变更纪律仍然适用。
