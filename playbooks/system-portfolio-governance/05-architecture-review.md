# 模板 05：架构评审机制

> **定位**：治理篇解决「决策怎么留痕」，本篇解决「谁在什么节点把关」。
> **产出**：评审分级表 + 一页纸材料模板 + 委员会运转规则 + 例外台账

---

## 一、评审到底在评审什么

先把目的说清楚，否则评审会退化成两种东西：**盖章会**（走过场）或**批斗会**（挑毛病）。

架构评审的唯一目的是：**在不可逆成本发生之前，把风险定价。**

由此推出三条原则：

1. **评审的是决策，不是文档**——没有「选项 ≥ 2 和代价对比」的材料，不进入评审；
2. **评审有时限**——评审不能成为项目的阻塞点，超时必须给出结论（通过/有条件通过/退回）；
3. **评审不替代负责人**——评审给的是风险判断，决策责任仍在项目负责人。

---

## 二、三级评审

| 级别 | 时点 | 回答的问题 | 材料最小集 | 参与人 |
|---|---|---|---|---|
| **L1 立项评审** | 项目启动前 | 该不该做？不做会怎样？ | 目标 + 约束 + 2 个以上方案 + 预估代价 | 架构 + 业务负责人 + 技术负责人 |
| **L2 方案评审** | 详细设计后、开发前 | 这么做有什么代价？出问题怎么退？ | 一页纸（见 §三）+ 关键时序/数据流 | 架构 + 相关领域负责人 + SRE |
| **L3 上线评审** | 首次上线前 | 出事了能不能止血？ | 回滚方案 + 监控项 + 容量结论 + 演练记录 | SRE + 架构 + 值班负责人 |

不是所有变更都要三级：**按不可逆性分级，而不是按项目大小**。

| 变更特征 | 最低评审级别 |
|---|---|
| 新增系统 / 更换核心存储 / 跨域数据共享 | L1 + L2 |
| 引入新的中间件或外部依赖 | L2 |
| 数据库不可逆变更（删字段、改语义） | L2 + L3 |
| 常规功能迭代 | 不评审，走发布流程 |
| 紧急修复 | 先做，48 小时内补记录 |

## 三、一页纸材料

评审材料超过一页，通常说明作者还没想清楚。最小集七项：

```
1. 目标：要解决什么问题，成功的判据是什么
2. 约束：时间、成本、团队能力、合规
3. 选项：至少两个，包含「不这么做」
4. 推荐：选哪个，为什么
5. 代价：这个选择放弃了什么（必须写）
6. 回滚：做错了怎么退，退的代价
7. 验证：上线后看哪三个指标判断成败
```

第 5 项是最常缺失、也最能分辨水平的：**写不出「放弃了什么」，说明没真正比较过。**

## 四、委员会怎么运转

| 项 | 规则（示例，按组织校准） |
|---|---|
| 组成 | 主席 1（架构负责人）+ 领域架构师 3–5 + SRE 1 + 安全 1 |
| 法定人数 | ≥ 3 人，且必须包含与议题相关的领域负责人 |
| 节奏 | 每周固定 60 分钟，议题提前 48 小时提交 |
| 决议时限 | 材料齐全后 3 个工作日内给出结论 |
| 决议类型 | 通过 / 有条件通过（列条件与期限）/ 退回补充 / 升级决策 |
| 异议记录 | 少数意见必须写入记录，不追求表面一致 |
| 回避 | 议题所属项目的直接负责人不参与表决 |

### 4.1 结论的写法

| 结论 | 必须附带 |
|---|---|
| 通过 | 记录关键假设与复审触发条件 |
| 有条件通过 | 条件、责任人、完成期限（到期未完成自动降级为退回） |
| 退回 | 缺什么、补什么、什么时候再提 |
| 升级 | 升级给谁、为什么委员会无法决策 |

**「有条件通过」是评审最常用的结论，也是最容易失效的**——条件不写 owner 和期限，等于通过。

### 4.2 评审记录

与 [治理决策记录](templates/03-governance-decision.md) 同构，字段对齐：编号、日期、议题、证据、选项、决定、条件、回滚、复审日期。

## 五、例外与破例

任何评审机制都会遇到「这次来不及了」。例外不可怕，**无记录的例外才可怕**。

| 项 | 规则 |
|---|---|
| 谁有权批 | 明确到角色（如架构负责人 + 技术负责人双签），不是「领导同意」 |
| 记录什么 | 破例理由、风险、补偿措施、有效期 |
| 有效期 | 默认 30 天，到期自动失效并复审 |
| 统计 | 每季度统计例外率，按系统/团队分布 |

**例外率是机制的体温计**：长期 > 20%，说明流程太重或门槛设错；长期为 0，说明要么没人敢提，要么统计失真。

## 六、效果度量

评审机制本身也要被评审。五个指标：

| 指标 | 定义 | 健康区间（示例） |
|---|---|---|
| 评审覆盖率 | 应评审变更中实际评审的比例 | ≥ 90% |
| 平均决议时长 | 材料齐全到给出结论 | ≤ 3 个工作日 |
| 返工率 | 退回补充的比例 | 10%–30% |
| 上线后 30 天事故率 | 评审过的项目 vs 未评审的 | 前者应显著更低 |
| 例外率 | 破例数 / 评审数 | ≤ 10% |

返工率过低（< 5%）通常不是质量好，而是评审太松或材料被提前「对齐」过。

## 七、四种失败形态

| 形态 | 表现 | 根因 | 处理 |
|---|---|---|---|
| **盖章会** | 5 分钟一个议题，全部通过 | 没有材料门槛 | 强制一页纸，无材料不上会 |
| **架构师瓶颈** | 所有事都等一个人 | 决策权未下放 | 分级授权，L2 可由领域架构师终裁 |
| **评审即结束** | 结论有了，条件没人跟 | 没有台账 | 条件进台账，月度回顾 |
| **只评新建，不评下线** | 系统只增不减 | 缺反向评审 | 下线决策同样走 L2（见治理闸门） |

最后一条尤其值得强调：**评审机制如果只管「建」，它就在系统性地制造熵增。**

---

## 八、小组织的版本

没有架构委员会也能运转，三件事即可：

1. **一个人 + 每周一个固定时段**：架构负责人每周留 2 小时专做评审，其余时间不接临时评审；
2. **一页纸模板 + 异步评审**：材料提前发，书面意见为主，只对分歧开会；
3. **一张例外台账**：所有「这次先不评」的变更登记在册，季度回看。

成本约每周 2 小时，换来的是「重大决策有据可查」——这在人员流动时价值最高。

---

## 九、与治理工具的衔接

- L1 立项评审 ↔ [组合治理](00-methodology.md) 的新建准入门：**没有退出条件的系统不允许立项**；
- L3 上线评审 ↔ [生产运维](../production-operations/) 的变更与演练：没演练过的切换方案不允许上线；
- 评审记录 ↔ [治理决策记录](templates/03-governance-decision.md)：同一套字段，同一个台账；
- 例外统计 ↔ [路线图与防回潮](templates/04-governance-roadmap.md) 的季度自检。

---

## 十、诚实边界

- 评审机制解决「决策质量的下限」，不解决「决策速度」——后者靠授权与分级；
- 小团队一人多角时，评审者与被评审者可能是同一人，此时机制的价值退化为「强制写下理由」，仍然有效；
- 本篇的时限、比例均为示例，需按组织节奏校准；
- 评审不能替代事后复盘：评审降低概率，复盘降低重复概率。
