# 00 架构组合治理方法论总纲

> **阶段**：总纲 ｜ **配套**：[模板 01–04](README.md#目录)
> 本篇全部示例、数字、系统名均为虚构，独立创作，不含任何真实企业信息。

---

## 一、为什么盘点经常白做

架构盘点在大多数组织的死法是固定的：

1. **为画图而盘点**——产出一张人人称赞、下季度就过期的架构全景图，没有产生任何决策；
2. **只盘不决**——问题清单列了 56 项，然后就没有然后了，P0 和 P3 享受同等待遇；
3. **决而无痕**——「领导说那套先留着」，半年后没人记得为什么留，于是它继续活着。

对症的药只有一条：**盘点从第一天起就为决策服务**。清单是证据，诊断是论证，决策记录才是产出。

---

## 二、四条原则

| 原则 | 一句话 | 操作化定义 |
|---|---|---|
| **盘点为决策服务** | 没有处置决策的盘点是白做 | 每轮盘点至少产出一条关停 / 合并 / 治理记录，否则复盘盘点本身 |
| **健康与价值分开评** | 没人用 ≠ 可以删；有人用 ≠ 健康 | 四象限先分价值再看健康，两轴独立打分（§五） |
| **处置按成本杠杆排序** | 能关停就不合并，能合并就不重建 | 五种处置的成本从低到高：关停 < 降配 < 治理 < 合并 < 重建（§五） |
| **防回潮比盘点重要** | 一次盘点管半年，闸门管永久 | 三道闸门：新建准入、依赖准入、下线默认（§七） |

四条原则与本仓库 [接手工程工具箱](../takeover-engineering/) 同源：证据分级管「判断的质量」，止损前置管「退出的成本」，决策记录管「组织的记忆」。

## 三、阶段一：清点——组合清单

目标：**一张表回答「我们有多少套系统、每套是什么」**。用 [模板 01](templates/01-portfolio-inventory.md)，每套系统一行，六个维度：

### 3.1 角色五分类（每套系统必须归一类）

| 角色 | 定义 | 例子（虚构） |
|---|---|---|
| **记录型** | 系统的权威数据在这里（订单、账务、库存） | `order-hub` 订单中心 |
| **流程型** | 驱动跨系统业务流转 | `settle-recon` 对账结算 |
| **门户型** | 面向人的入口，自身不持数据 | `member-portal` 会员门户 |
| **集成型** | 对接外部系统，做协议与数据转换 | `shop-gateway` 商城对接层 |
| **工具型** | 内部效率工具，无外部承诺 | `ops-console` 运维控制台 |

角色分类的价值：**门户型和工具型是天然的下线候选池**——它们死了没人索赔（前提是依赖方为零，见 3.3）。

### 3.2 活跃度三信号（全部来自可观测数据，不采信口头）

| 信号 | 取数 | 说明 |
|---|---|---|
| 最近发布 | 发布系统记录 | 超过 12 个月 → 候选休眠 |
| 90 天故障数 | 告警/工单系统 | 长期为 0 且无监控 ≠ 健康，可能是没人在看 |
| 依赖方数量 | 网关路由 + 调用链 | **0 依赖方是下线的最强证据** |

### 3.3 成本三件套

资源月成本（主机/中间件分摊）、维护人力（人天/月）、外部依赖费（第三方 API、许可证）。三件套让「僵尸良好系统」现形：**月成本真实存在，业务价值却为零**。

### 3.4 证据分级（与接手工程同源）

清单每一行的取数标注证据等级：**E1** 监控/发布系统实测 > **E2** 账单/工单记录 > **E3** 系统文档 > **E4** 负责人访谈 > **E5** 推断。**E4 及以下不许单独支撑处置决策**——「我听说那套没人用了」不是关停依据。

## 四、阶段二：诊断——四层下钻

用 [模板 02](templates/02-system-diagnosis.md)。触发时机：进入处置决策前、连续故障复盘后、或年度盘点抽样。**不必全量诊断**——全量清点，重点诊断（休眠候选、P0 故障户、成本前三各一套）。

| 层 | 查什么 | 典型发现 |
|---|---|---|
| **领域层** | 重复建设 / 越界（A 域系统干 B 域的活）/ 空心（只剩转发） | 两套系统各存一份主数据，冲突靠人工对账 |
| **架构层** | 单点 / 循环依赖 / 一致性机制缺失 | 核心库无主从，挂了全站停 |
| **工程层** | 构建可复现 / 测试基线 / 文档新鲜度 | 只有一个人能把它跑起来 |
| **运维层** | 监控覆盖 / 容量余量 / 成本效率 | 峰值余量 10 倍，纯浪费 |

问题按 **P0–P3** 分级，分级的定义只看一个字——**血**：

| 级 | 定义 | 响应 |
|---|---|---|
| P0 | 正在流血（生产事故、数据错误、安全暴露） | 本周内启动处置 |
| P1 | 季度内会流血（容量见底、单点无预案、依赖将 EOL） | 本季度进路线图 |
| P2 | 慢性病（不影响存活，持续消耗人力） | 年度盘点批量处置 |
| P3 | 可优化（记录在案即可） | 不排期，攒批 |

## 五、阶段三：决策——五种处置

### 5.1 四象限：先价值，后健康

| | **健康** | **不健康** |
|---|---|---|
| **高业务价值** | 维持（但别忘了健康也会过期） | **治理**（还债）或 **重建**（还不了债时） |
| **低业务价值** | **降配 / 合并**（僵尸良好系统的归宿） | **关停**（第一优先，立即执行） |

两个容易踩的坑：

- **低价值高健康是最容易被放过的浪费**——它运行良好、没人抱怨、所以没人想起它。它的正确处置是降配或并入相邻系统，不是维持；
- **高价值不健康的系统永远排在路线图最前**——这是组织真正疼的地方。

### 5.2 成本杠杆排序（原则三的展开）

```
关停   成本≈迁移归档 + 沟通     ← 永远先问：能不能直接关？
降配   成本≈资源调整
治理   成本≈专项人月（还债）
合并   成本≈双系统迁移期（最贵的日常处置）
重建   成本≈新项目立项           ← 万不得已才走
```

决策会议的第一问永远是：**「这个处置是不是可以再降一级？」**——能关停的方案不要提合并，能治理的方案不要提重建。

### 5.3 决策记录：ADR 的治理变体

每条处置用 [模板 03](templates/03-governance-decision.md) 留痕，与本仓库 ADR 文化同构：**背景 / 证据 / 选项（≥2）/ 决定 / 回滚条件 / 复审日期**。两条强制规则：

1. **无 ≥E2 证据不得关停**——对称地，**无 ≥E2 证据也不得拒绝关停**（「再看看」必须给出证据和复审日期）；
2. **每条关停必须写回滚条件**——数据保留多久、接口坟场（返回明确错误码的影子端点）保留多久、谁有权叫停。

## 六、阶段四：执行——路线图

用 [模板 04](templates/04-governance-roadmap.md) 把决策记录排进**季度路线图**。排序规则：P0 > P1；同一级按成本杠杆（关停先于合并）。每个季度的量宁少勿全——**一个季度真实关闭 3 套系统，好过排期 15 套只关了 1 套**。后者会摧毁整个治理机制的信用。

执行的完成标准不是「上线了」，是**组合清单上那一行的状态改了**。清单是唯一权威源（Single Source of Truth）——这正是治理版的「一个概念，一个词」，与 [工程一致性规范](../engineering-consistency-standards.md) 同一思想。

## 七、防回潮：三道闸门

盘点是快照，闸门是制度。没有闸门的治理，一年后从头再来。

| 闸门 | 规则 | 拦住什么 |
|---|---|---|
| **新建准入** | 新系统立项必须先在组合清单占一行：分配 ID、声明角色、声明与既有系统的关系（新建 / 替换 / 并存） | 重复建设——立项会上先回答「为什么不是给现有系统加个模块」 |
| **依赖准入** | 引入新中间件 / 框架 / 外部服务，过一次轻量架构评审（≤1 页纸：场景、备选、退出成本） | 技术栈发散——每个多余的中间件都是未来盘点时的一列成本 |
| **下线默认** | 连续 12 个月无发布、0 依赖方的系统，**自动**进入下线复审（不需要任何人提议） | 僵尸良好系统——让「遗忘」不再等于「存活」 |

闸门的执行载体是流程卡点（立项表单、评审会、脚本扫描），不是倡议。**需要人自觉的闸门不是闸门。**

评审会这一载体怎么运转、材料多厚、谁有权破例，见 [模板 05 架构评审机制](05-architecture-review.md)——闸门没有组织承接，就只是文档里的一行字。

## 八、贯穿示例（虚构）

一家 35 套系统的中型商贸企业，一轮 6 周的治理盘点，实际产出：

| 阶段 | 产出 | 关键判断 |
|---|---|---|
| 清点 | 35 行组合清单，4 套标注 E5 待补证 | 「35 套」这个数字第一次有权威版本 |
| 诊断 | 12 套进入重点诊断，2 项 P0（核心库单点）、5 项 P1 | 空心系统 3 套，全是门户型 |
| 决策 | 6 条决策记录：关停 3、降配 1、治理 2 | 关停的 3 套全是「0 依赖方 + 12 个月无发布」 |
| 执行 | 季度路线图 Q1 关停 2、Q2 关停 1 + 治理 2 | 三道闸门同步上线 |

半年后的增量复审：新立项 4 套系统全部先行入册；下线默认闸门自动揪出 1 套新僵尸。**盘点一次的成本，换回了制度性的减法能力。**

## 九、诚实边界

- 本方法论适用于**中等规模（15–100 套）系统群**。超过 100 套，清点要配工具（CMDB / 调用链平台），人工表格撑不住；
- 没有覆盖组织政治面：关停动了谁的地盘、谁的预算——决策记录能对冲一部分（留痕给上级和审计），对冲不了全部。技术负责人需要的另一半能力在这本工具箱之外；
- 示例数字全部虚构，不构成任何行业基准。
