> **版本**：v0.1 ｜ **日期**：2026-10-24 ｜ **状态**：已随本仓库发布
> **定位**：系统进入持有期之后的熵增治理——怎么清点、怎么诊断、哪些该关停合并、怎么防止回潮。

## 与姊妹篇的关系

| | [接手工程工具箱](../takeover-engineering/) | 本工具箱 | [生产运维](../production-operations/) |
|---|---|---|---|
| 管什么 | **进入时**：该不该接、接多少、报多少钱、什么时候停 | **持有期间**：哪些该关、哪些该治、怎么防止只增不减 | **运行期**：怎么让它稳定活着 |
| 典型触发 | 有人递来一个不属于你的系统 | 系统数量涨到没人说得清全貌 | 出事才发现、变更失控、救火靠英雄 |
| 止损思想 | L0–L3 投入封顶、确认单到期自动暂停 | 12 个月无发布自动进下线复审 | 变更必须可回滚、告警必须可执行 |

三者共享同一套底层判断：**证据分级**（盘点结论同样不许把推断当事实）、**止损前置**（下线条件在建系统时就该想到）、**决策留痕**（关停一套系统和接一个项目一样需要决策记录）。治理的诊断结论也直接喂给运维：长期无演练、容量见底无计划，都是低健康度的证据。

## 它解决什么问题

系统数量过了 20 套，熵增开始显形：

1. **说不清全貌**——「我们有多少套系统」这个问题，运维、架构、财务各有一个答案；
2. **只增不减**——新建永远有预算，下线永远没排期。「僵尸良好系统」（没人用、但还在正常运行、还在烧维护成本）是最容易被忽略的浪费；
3. **领域失衡**——有的域五套系统干一件事，有的域零套系统全靠表格；
4. **决策靠嗓门**——关停哪套系统，取决于谁声音大，不取决于证据。

本工具箱把治理拆成**四个阶段、四条原则、五份可直接填写的模板**，产出不是一张更漂亮的架构图，而是一串**可执行、可回滚、可复审的处置决策**。

## 使用节奏

| 节奏 | 动作 | 量级 |
|---|---|---|
| **年度大盘点** | 全量清点 + 重点诊断 | 4–8 周（30–50 套系统规模） |
| **季度增量复审** | 新系统入册、P0/P1 复查、路线图推进 | 1–2 天会议 + 各系统负责人填表 |
| **即时入册** | 任何新系统立项，先在组合清单占一行 | 半小时——这是防回潮的第一道闸门 |

> 盘点的产出是**决策**，不是表格。如果一轮盘点结束没有产生任何一条「关停 / 合并 / 治理」记录，那不是盘点成功，是盘点白做——见 [00 方法论](00-methodology.md) 原则一。
