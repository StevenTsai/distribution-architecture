# 工程一致性规范（模板）

> **版本**：v0.1 ｜ **日期**：2026-10-24
> **定位**：给 5–50 人研发团队直接套用的工程一致性基线。八章，每章分「强制 / 推荐」，附自检清单。
> **权利声明**：独立创作。所有示例、命名、系统名均为虚构，不含任何任职雇主的规范原文表达。
> **用法**：复制到自己仓库 → 删掉用不上的 → **把「推荐」升为「强制」的前提是有 CI 卡点**，没有卡点的强制只是愿望。

---

## 为什么是一致性，不是规范

规范清单有成百上千条，团队记不住。真正被遵守的规范往往只有一条底层公理：

> **一个概念，一个词，一处权威。**

同一个业务概念，在工程名、数据库、接口、配置、告警里必须叫同一个名字；同一个事实，只有一处数据是权威的；同一个约定，只有一份文档说了算。本规范八章都是这条公理的展开。

强制与推荐的含义：

| 级别 | 含义 | 违反后果 |
|---|---|---|
| **强制** | CI / 评审卡点拦截 | 合不进去 |
| **推荐** | 评审时优先遵循，偏离需说明 | 记录在案，不拦截 |

## 第一章 命名（强制为主）

### 1.1 工程与服务名

```
<域>-<系统>[-<模块>]     全小写，连字符
```

示例（虚构）：`order-hub`、`order-hub-api`、`settle-recon`、`shop-gateway`。禁止：驼峰、下划线、大小写混用、无域前缀的裸名（`common-utils` 这类名字禁止出现在生产工程）。

### 1.2 数据库与表

```
数据库：<域>_<系统>          如 order_hub
表：t_<域>_<名>            如 t_order_main、t_order_item
```

### 1.3 HTTP 接口路径

```
/v1/<资源复数>              如 /v1/orders、/v1/settlements
```

版本进路径（见第二章）；动词只允许标准表：`create` `get` `list` `update` `cancel` `confirm`——用名词做资源，用 HTTP 方法表达动作，不用 `/createOrder`。

### 1.4 配置键

```
app.<系统>.<组件>.<键>       如 app.order-hub.retry.max-attempts
```

### 1.5 术语标准库（强制机制，推荐内容）

每域维护一张**中英对照表**：业务概念 → 唯一英文词。例：下单 = `place order`（不许混用 `create/submit/new`）；对账 = `reconcile`（不许混用 `check/balance`）。新词入表走评审——**表里没有的词，代码里不许出现**。

> 自检：全局搜一个业务概念的英文，命中超过两个拼法的，本月内收敛。

## 第二章 版本（强制为主）

### 2.1 语义化版本三段

`MAJOR.MINOR.PATCH`——**第一位 = 不兼容变更，第二位 = 向后兼容的功能，第三位 = 修复**。发布 tag = 版本号 = 镜像 tag，三者强制绑定同一字符串。

### 2.2 分支命名（强制）

```
feature/YYYYMM/vX.Y[.Z]     如 feature/202610/v3.28
hotfix/YYYYMM/vX.Y.Z-patch  如 hotfix/202610/v3.28.1
```

分支名自带目标版本，发布日历上一眼看出谁在哪趟车上。

### 2.3 数据库迁移（强制）

迁移脚本序号**只增不改**：`V12__add_order_source.sql` 一旦合入，内容永不修改——修错了加新脚本。回滚脚本与迁移脚本成对存在。

### 2.4 对外 API 版本（强制）

破坏性变更 = 新路径版本（`/v2/`），旧版本保留期 ≥ 一个业务季度，并在响应头返回弃用通知。

## 第三章 工程结构（推荐为主）

统一骨架，模块边界即团队边界：

```
<工程根>/
├── api/        对外接口定义（DTO、契约、错误码）
├── service/    业务逻辑（不依赖具体框架的纯逻辑尽量上浮）
├── infra/      基础设施适配（DB、MQ、外部调用）
├── config/     配置类与默认值
├── db/         迁移脚本（只增不改）
└── docs/       本系统文档（架构图、README、runbook）
```

配套推荐：`service` 不 import `infra` 的具体类（面向接口）；测试目录镜像主目录。违反结构的例外在 README 记录例外原因——**例外要留痕，否则结构失去意义**。

## 第四章 接口（强制为主）

### 4.1 统一响应信封（强制）

```json
{ "code": 0, "message": "ok", "data": { }, "traceId": "..." }
```

### 4.2 错误码分段（强制）

| 段 | 含义 |
|---|---|
| 1xxxx | 参数/校验错误（调用方的错） |
| 2xxxx | 业务规则错误（可预期的拒绝） |
| 3xxxx | 外部依赖错误（可重试的边界） |
| 5xxxx | 内部错误（不该发生，告警要响） |

错误码进错误码登记表（一处权威）；`message` 面向人读，`code` 面向程序判断——**不许前端解析 message**。

### 4.3 分页与时间（强制）

分页统一 `page`（从 1 起）+ `size`（上限 200）+ 返回 `total`；时间统一 ISO 8601 带时区（`2026-10-24T15:30:00+08:00`），**库内 UTC，展示层转时区**。

### 4.4 新对接七问（强制记录）

与外部系统对接前，七个问题必须有书面答案（与接手工程的 [21 问](takeover-engineering/hooks/21-questions.md)同源，这是接口尺度的子集）：

1. 对方接口的版本与变更通知机制？
2. 超时、重试、幂等分别怎么定义？
3. 限流阈值与被限流时的表现？
4. 错误码表在哪，谁维护？
5. 数据的权威方是谁（冲突时以谁为准）？
6. 联调环境与测试数据怎么来？
7. 对方故障时，我方降级方案是什么？

## 第五章 配置与环境（强制）

### 5.1 三源分级

```
代码默认值  <  环境配置文件  <  环境变量注入
```

优先级高的覆盖低的；**安全类配置（密钥、证书、连接凭证）只允许第三级**——不许进代码、不许进配置文件、不许进 Git。

### 5.2 密钥红线（强制，CI 拦截）

CI 扫描命中密钥模式即构建失败。生产启动时对关键密钥做占位符检测：**占位符未替换则拒绝启动**（fail-fast，宁可不起也不裸奔——与本仓库 [生产护栏案例](../case-studies/production-guardrails/) 同一思想）。

### 5.3 环境命名（强制）

四套封顶：`dev` / `test` / `staging` / `prod`。不许出现 `dev2`、`test-new`、`prod-pre` 这类野生环境名——环境数量是乘法风险。

## 第六章 迭代与发布（推荐为主）

- **发布节奏**：固定窗口（如每周二、四下午），窗口外发布走 hotfix 流程并事后补复盘；
- **发布清单最小集**：变更范围 / 回滚方案（写不出来不发）/ 观察指标（发布后 30 分钟看哪三块板）；
- **回滚预案强制**：任何发布，回滚步骤在发布单上提前写好——**现场发明的回滚不是回滚，是二次事故**。

---

## 第七章 健康度最小指标（推荐）

五个指标，月度看板，指标异常先查根因再追责：

| 指标 | 定义 | 红线（示例，按团队校准） |
|---|---|---|
| 构建时长 | 主干全量构建 P50 | > 15 分钟开始治理 |
| 测试通过率 | 主干最近一次构建 | < 100% 超 2 天 = P1 |
| 二次故障率 | 同根因 30 天内复发 | > 0 = 复盘质量不达标 |
| 变更回滚率 | 月度回滚次数 / 发布次数 | > 10% = 发布流程收紧 |
| 文档新鲜度 | README/架构图更新 vs 最近发布 | 落后 3 个版本 = 该系统健康度扣分 |

## 第八章 术语表：统一语言（强制）

前七章管的是「怎么写」，这一章管「说的是不是同一件事」。**命名不一致的根源，往往是概念没对齐**——代码里叫 `merchant`、库表叫 `shop`、接口叫 `store`、产品文档叫「门店」，四拨人对同一个东西有四种理解，任何规范都救不了。

### 8.1 三条规则

1. **一个概念，一个词**：中文、英文、缩写各只能有一个；
2. **一个词，一个定义**：不允许「根据语境不同含义不同」；
3. **一处权威**：术语表是唯一权威源，代码、接口、文档、UI 文案都必须引用它，不得各自发明。

### 8.2 术语表模板

| 术语（中/英） | 定义 | 明确不是（反例） | 代码标识 | 权威位置 | owner | 状态 |
|---|---|---|---|---|---|---|
| 客户 / customer | 与平台签约的主体 | 不是「下单人」，也不是「收货人」 | `Customer` | 术语表 v1 | 领域负责人 | 生效 |
| 门店 / store | 客户下属的经营场所 | 不是「仓库」 | `Store` | 术语表 v1 | 领域负责人 | 生效 |
| 结算单 / settlement | 一个结算周期内应收应付的汇总 | 不是「对账单」 | `Settlement` | 术语表 v1 | 财务域 | 生效 |

「明确不是」这一列比定义更重要——**大多数歧义不是不知道它是什么，而是把它和邻居搞混了。**

### 8.3 三处映射

同一个术语必须在四个地方保持一致，任何一处不一致都算缺陷：

| 位置 | 要求 |
|---|---|
| 领域模型 / 代码 | 类名、方法名、变量名使用英文标识 |
| 数据库 | 表名、字段名与代码标识对应，不做二次翻译 |
| 接口 | 请求/响应字段名、错误码文案使用同一术语 |
| 用户界面 | 文案使用中文术语，不使用同义词 |

### 8.4 改名纪律

术语改名不是改文案，是一次数据与契约的迁移：

- 先加新词（代码、字段、接口并行支持）；
- 双写/回填，确认无旧词流量；
- 再删旧词，且删除必须晚于所有调用方下线。

**禁止**在需求里悄悄换词、禁止同一版本内既加新词又删旧词——与数据库的 expand–contract 是同一条纪律。

### 8.5 最小落地

不必一次建全。先做三件事：

1. 列出核心域 **20 个**最高频名词，每个写一行定义与反例；
2. 在代码评审清单里加一条：**新增/修改的领域名词，是否已在术语表？**
3. 每季度做一次「表外同义词」扫描：全局搜索同义词（如同时出现 `shop`/`store`/`merchant`），逐条归并。

> 术语表与 [领域模型](../tutorial/01-domain-model.md) 是同一件事的两种表达：模型说「它们是什么关系」，术语表说「我们怎么称呼它」。两者脱节，模型就会在代码里走样。

## 落地路径（渐进生效）

不许第一天全量强制——那会让团队绕过规范而不是遵守规范：

| 月份 | 升为强制 | 理由 |
|---|---|---|
| 第 1 月 | 命名（1.1–1.4）+ 术语表（第八章）+ 密钥红线（5.2） | 改起来最便宜，且密钥零容忍 |
| 第 2 月 | 响应信封 + 错误码分段 + 版本绑定 | 跨团队协作的摩擦点 |
| 第 3 月 | 迁移只增不改 + 环境命名封顶 | 需要工具链配合 |
| 之后 | 推荐项按痛点逐个升强制 | 每升一条，先有卡点再改文本 |

> 本规范是**下限，不是上限**。团队可以在此之上细化，但细化不得与本基线相悖——「不相悖」的判定权归架构评审，特例以书面记录形式存在。

## 自检清单（每季度）

- [ ] 术语标准库是否更新？代码中是否出现表外同义词？
- [ ] 全局搜索密钥模式（CI 历史）：零命中？
- [ ] 错误码登记表与代码一致性抽查：10 条抽查零偏差？
- [ ] 迁移脚本是否存在已合入后被修改的（V 编号复用）？应为 0
- [ ] 环境清单是否仍为四套封顶？
- [ ] 月度健康度五指标是否全部有数？异常项是否有根因记录？
