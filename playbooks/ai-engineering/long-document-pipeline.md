# 长文档多阶段生成：把不可控的大调用拆成可验证的小阶段

> 上下文窗口变大，不等于长文档任务自动变稳定。输入长、输出长、结构严格、还要继续下游处理时，一次调用同时承担了太多责任。
>
> 本文给出一种三段式结构：**分段审阅 → 可审查改写 → 全文重组**。

---

## 一、什么时候不该一次调用

以下条件同时出现时，应评估拆分：

- 输入超过单次稳定处理范围；
- 输出也需要较长文本或复杂结构；
- 失败后重跑整份文档成本很高；
- 用户需要知道每条结论来自哪里；
- 中间结果需要人工审查；
- 任务包含几种不同性质的子任务。

典型反例是合同审阅：一次调用同时要求理解全文、识别风险、分级、找缺失条款、生成 JSON，再基于结果改写全文。任何一处截断都会污染后续所有阶段。

---

## 二、三段式流程

```mermaid
flowchart LR
    D[原始长文档] --> C1[稳定切片]
    C1 --> R[阶段一：分段审阅]
    R --> M[合并与去重]
    M --> W[阶段二：生成改写意图]
    W --> A[阶段三：位置绑定与全文重组]
    A --> V[一致性检查]
```

### 2.1 阶段一：分段审阅

每个片段只回答局部问题：

```text
这一段存在哪些可以定位的风险或缺失线索？
证据在原文什么位置？
```

不要在这一阶段要求模型完成全文总结、优先级排序和最终判断。

输出至少包含：

- 稳定片段 ID；
- 原文起止位置或可定位引文；
- 风险/问题类型；
- 局部证据；
- 不确定性和缺失信息。

最后再做一次合并：

- 去重；
- 统一命名；
- 合并相同根因；
- 检查局部证据是否跨片段拼接；
- 明确哪些问题需要全文上下文才能判断。

### 2.2 阶段二：生成可审查的改写意图

不要直接让模型生成一份“最终完整文档”。先生成结构化修改清单：

```json
{
  "issueId": "...",
  "targetRef": "...",
  "originalText": "...",
  "replacement": "...",
  "reason": "...",
  "confidence": "..."
}
```

这一层是审查边界：人或其他程序可以逐条接受、拒绝、修改，并明确改动是基于哪个问题发生的。

按两类任务分别处理：

- **已有内容的改写**：必须绑定原文位置；
- **缺失内容的补写**：必须说明为何缺失、应插入哪里。

两者混在一次 Prompt 中，模型容易把“新增条款”误当成“改写原条款”。

### 2.3 阶段三：全文重组

全文重组不是让模型重新自由创作，而是把已确认的修改意图绑定回原文位置。

绑定顺序建议：

1. 精确原文命中；
2. 稳定锚点或标题命中；
3. 找不到唯一位置时标记“待人工确认”。

不允许静默插入任意片段。对未修改内容，应尽量原样保留，降低无关改写风险。

---

## 三、阶段之间必须有契约

多阶段系统最常见的错误是“每段都返回了 JSON，就认为可以串起来”。阶段之间需要明确契约：

| 契约 | 要回答的问题 |
|---|---|
| 标识 | 片段、问题、证据和改写如何稳定关联？ |
| 完备性 | 哪些字段必须存在，哪些可为空？ |
| 唯一性 | 同一问题重复出现如何合并？ |
| 定位 | 文本位置如何校验和回绑？ |
| 失败 | 某一段失败时整任务停止还是局部重试？ |
| 版本 | 文档、提示词、模型和规则版本如何固定？ |

没有这些契约，只是把一次大黑箱拆成了多个小一点的黑箱。

---

## 四、切片策略

切片不应只按固定字符数机械切割。至少考虑：

- 章节或条款边界；
- 标题与交叉引用；
- 表格、页眉和脚注；
- 重叠窗口；
- 文档语言与编码；
- 页级或段落级原文坐标。

重叠窗口用于保留上下文，但重复内容必须在合并阶段去重。每个片段都要有稳定 ID 和原文范围，不能只依赖片段在数组中的序号。

---

## 五、失败与重试

每个阶段独立记录状态：

```text
PENDING -> RUNNING -> VALIDATED -> MERGED
                    -> RETRYABLE_FAILED
                    -> PERMANENT_FAILED
```

重试原则：

- 某一段结构失败，只重跑该段；
- merge 失败，只重跑 merge；
- 位置绑定失败，不重新生成整份文本；
- 模型或提示词版本变化后，不复用旧阶段结果；
- 永久失败必须暴露给用户，不能悄悄跳过。

还需要设置整个任务的总预算，防止局部重试叠加成不可控成本。

---

## 六、合并阶段的责任

合并不是简单字符串拼接。它需要：

- 按稳定 ID 去重；
- 统一问题分类和严重度；
- 合并相同根因；
- 解决片段间的矛盾；
- 保留所有证据引用；
- 标记无法自动裁决的分歧；
- 检查汇总数量是否与明细一致。

跨片段组合出的结论必须回到同一证据中重新验证，不能把 A 段的实体和 B 段的数字自动拼成一条“有出处”的结论。

---

## 七、质量指标

| 指标 | 说明 |
|---|---|
| 阶段成功率 | 定位失败发生在哪一段 |
| 局部重试率 | 判断拆分是否真正降低了重跑成本 |
| 证据绑定率 | 每条问题是否有可定位证据 |
| 去重率 | 合并阶段消除了多少重复 |
| 未绑定改写数 | 无法安全放回原文的修改数量 |
| 人工接受率 | 修改意图是否真的有用 |
| 全长保留率 | 未修改内容是否被原样保留 |
| 原文覆盖率 | 所有片段和条款是否均被处理 |

只统计“最终文档生成成功”会掩盖漏段、重复和位置错绑。

---

## 八、常见错误

1. **只按字符数切片**：截断条款、标题和表格；
2. **局部片段要求全局结论**：模型只能猜测未见内容；
3. **直接生成完整修订稿**：没有中间审查层，无法判断改了什么；
4. **Rewrite 找不到位置就随便插入**：最终文档结构被破坏；
5. **局部失败静默跳过**：结果看似成功，实际漏审；
6. **每次重试都换模型或 Prompt**：阶段结果无法比较；
7. **把拼接当合并**：重复、矛盾和计数错误没有处理。

---

## 九、落地检查清单

- [ ] 已定义进入多阶段处理的长度与复杂度阈值；
- [ ] 切片尊重章节、段落和引用边界；
- [ ] 每个片段、问题、证据和改写都有稳定 ID；
- [ ] 阶段之间有明确输入输出契约；
- [ ] 修改意图可审查，不直接生成黑箱全文；
- [ ] 改写能绑定回原文，否则标记人工确认；
- [ ] 局部失败只触发局部重试；
- [ ] 合并阶段负责去重、计数与矛盾披露；
- [ ] 全文覆盖率、证据绑定率和未绑定改写数可观测；
- [ ] 任务总成本和重试预算有上限。

---

## 十、诚实边界

- 拆分增加调用次数和编排复杂度，短文档不应默认套用；
- 局部审阅可能缺少全文语境，因此必须保留“需要全文判断”的标记；
- 自动合并不能替代专业判断，高风险文档仍需人工确认；
- 文章中的长度阈值和阶段划分来自具体工程场景，迁移时需要按模型、文档结构和质量目标重新校准。
