# AI 工程实践（AI Engineering Playbook）

> **定位**：把大模型应用从“能调用”推进到“能控制失败、能估算成本、能定位问题”的工程方法。
>
> **范围**：结构化输出治理、多模型路由、长文档多阶段生成。本文档不讨论模型排行榜，也不把某一家 Provider 的能力当成架构前提。

---

## 为什么需要这一层

RAG 校验门解决的是**结果交付前能不能被信任**；这里补的是另一半问题：

1. 模型返回的 JSON 能不能进入业务系统？
2. Provider 超时、限流或输出异常时，整条链路会不会一起失败？
3. 长文本和长输出能否拆成可重试、可定位、可审查的阶段？

只做输出校验而不做生成链路治理，系统会出现一种错觉：校验越来越严格，任务却越来越频繁地整体失败。

## 推荐阅读顺序

```mermaid
flowchart LR
    A[定义单次调用边界] --> B[隔离 Provider 失败]
    B --> C[拆分长文档阶段]
    C --> D[交给确定性校验门]
```

先做单次调用边界，再做故障隔离，最后拆阶段。顺序反了，阶段编排只会把不稳定放大到更多调用。

## 证据边界

这些方法提炼自法律与通用 AI 应用工程实践。文章中的调用次数、阈值和成本数据依赖具体任务、模型版本与上下文长度，不构成行业基准；本仓库不附带对应私有业务代码、提示词或真实用户数据。
