# 开源发布止血带：私有生产到公开模式库的提取卫生

> 全开泄露，全关没人用。切分线不是一句免责声明，是设计出来的。

---

## 一、问题出在提取环节，不在发布环节

这本仓库的每个 case study 都来自私有生产系统。所有文档里都有同一句话："仅提取通用架构模式，不包含业务敏感配置和客户数据。"

这句话是承诺，不是工艺。**泄露从来不是在 push 那一刻发生的——它发生在提取环节**：写文档的人脑子里装着客户名、内部代号、未公开的业务数字，笔会先于意识泄露。等到了发布前检查，错误已经在文档历史里了。

本 playbook 把提取卫生固化成四件可执行的事：**画切分线、扫描器开源/词表闭源、推送前清单、数据边界声明**。全部来自一个真实项目的完整实践——[GroundedRAG](https://github.com/StevenTsai/grounded-rag) 的开源过程（其架构背景见[声明级校验门](../architecture/claim-level-verifier.md)与[失败复盘](../architecture/verifier-failure-modes.md)）。

## 二、切分线：什么留私有，什么进公开

GroundedRAG 的前身是一个私有医疗域系统。开源时的切分结果：

| 能力 | 私有侧（不进仓库） | 公开侧（进仓库） | 切分依据 |
|------|------|------|------|
| 领域数据 | 生产病历数据 | 合成示例数据 | 数据本身不可让渡 |
| 合规判定逻辑 | PHI 脱敏链路 | 无 | 合规相关，随数据责任走 |
| 待专利机制 | 规则引擎 skip 语义等 | 无 | 专利申请前不公开 |
| 可判定通用机制 | — | 校验门、评测口径、多模型兜底 | 可脱离领域独立验证 |
| 失败与边界数据 | — | E2E 落差、对照实验实录 | 该项目失败数据已人工确认可公开 |

三条判断标准，逐条过：

1. **含领域专有数据？** 有 → 留私有（或替换为合成数据后再议）；
2. **含合规判定逻辑？** 有 → 留私有（它随数据责任走，不随代码走）；
3. **是待专利保护机制？** 是 → 留私有，**且在专利申请日前不要公开**——在先申请制语境下，自愿公开即构成现有技术（此判断仅限**专利新颖性**维度；合同义务、第三方数据、出口管制等其他知识产权问题需单独评估）。

不命中以上三条、又能脱离领域独立验证的机制，进公开侧。切分线画错的两种死法是对称的：**泄了不可逆；过度封闭则公开侧无法独立验证，等于没人用。**

一条反过来的好消息：**已经公开的部分，就专利新颖性而言**写进文档、演讲、书籍不会再损（其他知识产权维度仍需单独判断）。所以审计顺序永远是先确认"线画在哪"，再决定"能写什么"。

## 三、扫描器开源，词表闭源

泄露扫描器本身怎么处理？GroundedRAG 的答案是一个可直接复用的模式：

```
tools/leak_scan.py          ← 扫描逻辑入库：可审计、可 fork、可进 CI
.leak_markers.example.json  ← 词表模板入库：只含占位词
.leak_markers.json          ← 真实私有词表：不入库，本地维护
```

三个决策点：

1. **扫描逻辑必须开源。** 闭源扫描器无法被社区审计，你也没法让贡献者信任它。逻辑里不该有任何秘密；
2. **词表必须闭源。** 私有词表本身就是泄露面——一份"内部代号 + 客户名 + 未公开术语"的列表跟着扫描器一起开源，等于把泄露清单开源。词表走本地文件并加入 `.gitignore`（"不入库"靠 ignore 规则保证，不靠记性），仓库里只留 example 模板；
3. **"改写"不等于"清库"。** 从内部文档改写段落进开源仓库，语义相似度仍然很高。对疑似参考的内部材料，先跑相似度核对：

   ```bash
   python tools/leak_scan.py --refs <内部文档目录> --threshold 0.5
   ```

   高相似度文件要么重写到真正独立，要么放弃收录。注意相似度是**整文件**字符 bigram 比对——长文件里夹带单段搬运会被稀释，分数低不等于干净；这一步必须配合人工抽查。

## 四、推送前清单

每次 push 前逐条过，任何一条不满足都不应推。前七条来自 GroundedRAG 的 CONTRIBUTING；第 8 条是本 playbook 的追加——源清单只扫当前工作树，对"提取自私有系统"的仓库不够：

1. [ ] 测试全绿、静态检查无告警（`pytest` / `ruff check`）；
2. [ ] 评测口径复核：自建评测指标为预期值（口径定义见其 [docs/metrics.md](https://github.com/StevenTsai/grounded-rag/blob/v1.0.0/docs/metrics.md)）；
3. [ ] 泄露扫描退出码 0（`python tools/leak_scan.py`）；
4. [ ] 疑似参考的内部文档/草稿，已跑 `--refs` 相似度核对；
5. [ ] 私有词表已写入 `.leak_markers.json`，且该文件已在 `.gitignore` 中，并带 `--markers` 显式指定后重跑一次扫描；
6. [ ] 数据合规：`examples/` 只允许自研合成数据；由公开指南/文献整理的真实评测数据（含第三方内容）**不得入库**，仅本地维护并标注来源；新增依赖已核对许可证并更新第三方声明清单；
7. [ ] 涉及行为语义的改动，已同步 README / docs 中的口径说明与示例；
8. [ ] `.git` 历史与已推送分支已检查，无敏感提交；若有，轮换相关凭据（密钥、token、密码），并评估历史重写（`git filter-repo`，不可逆，需单独决策）。

清单的价值不在工具能拦的条目（第 3、5 条），在靠人判断的条目（第 4、6、8 条——尤其是第 8 条：历史泄露一旦发生不可逆转，止损手段只有轮换和重写）。把判断题写成清单，是为了让"这次就不用了吧"有一个明确的勾选动作可以省略——省略必须是显式的。

## 五、数据边界与第三方声明

三条基线，全部对公开可见：

1. **入库的只有合成/自研数据。** 示例数据、评测集、demo 输入，一律合成；
2. **真实评测集本地维护，声明可审阅。** 不入库，但在 README 里明说它存在、怎么编纂、可应请求供审阅——"不存在"和"不入库但可审阅"是诚实度完全不同的两种声明；
3. **第三方内容进声明清单。** 每个依赖、每份引用资料的许可证进 `THIRD_PARTY_NOTICES`；数据来源单列一节。第三方内容的边界不靠记忆，靠清单。

配套地，在 README 的显著位置声明数据口径与免责声明（如"演示数据为合成，非医疗建议"）——**诚实边界公开可见，本身就是信任资产。**

## 六、诚实边界

- 这套工艺防**呆**不防**坏**：漏检永远可能，词表有覆盖盲区，相似度阈值要按域校准；
- 清单和工具**不能替代法律审查**——涉及专利申请日、第三方许可证、数据出境的判断，过完清单仍然要过专业意见；
- 切分线的判断标准（本文第二节的三条）来自一个医疗域项目的实践，其他域（金融、政务、IoT）的"合规判定逻辑"边界要重新画；
- "扫描器开源、词表闭源"解决了词表泄露，但解决不了**行为泄露**——如果公开代码的接口形状本身暴露了私有系统的业务结构，那是切分线的问题，不是扫描器的问题。

- 扫描器可独立运行：

  ```bash
  git clone https://github.com/StevenTsai/grounded-rag && cd grounded-rag
  git checkout v1.0.0
  python tools/leak_scan.py \
    --root <你的仓库路径> \
    --markers <你的仓库路径>/.leak_markers.json    # 扫你的仓库并读你的私有词表
  python tools/leak_scan.py                        # 不带参数则扫扫描器所在仓库自检
  ```

  注意 `--markers` 默认按**当前工作目录**解析（读 `./.leak_markers.json` 若存在），不跟随 `--root`——扫外部仓库时必须显式传入目标仓库的词表路径。
