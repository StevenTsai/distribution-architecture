# ADR: 后端框架由 NestJS 计划改为 Spring Boot 单轨

中文 | [English](../en/decisions/why-spring-boot-not-nestjs.md)

> 状态：已采纳
> 日期：2026-09（规划）→ 2026-10（收敛为单轨）
> 决策者：架构团队

---

## 背景

规划阶段的后端选型是 **NestJS + MySQL 8 + Redis + COS + Docker**：Node 全栈（小程序 + 后端同语言）、TypeScript 装饰器风格接近 Angular、迭代快。

实施中整体替换为 **Java 17 + Spring Boot 3.2 单轨**：Redis 降级为[可插拔备选](why-redis-optional.md)、COS 未接入（本地磁盘）、Docker 未使用；Node 侧实现**冻结**，仅保留为跨语言对拍基准。

这个替换经常被质疑为"团队技术栈偏好"。本 ADR 的目的是给出**可从代码验证的四条收益**——如果收益不能落到具体的框架机制上，偏好就不该被写成决策。

## 决策

后端单轨 Java 17 + Spring Boot 3.2。规划中的 NestJS 实现不再推进；已有的 Node 基线实现冻结为对拍参照，不进生产。

## 考虑的替代方案

### 方案 A：按规划推进 NestJS

| 维度 | NestJS | Spring Boot |
|---|---|---|
| 语言一致性 | 与小程序同为 JS/TS 生态 | 独立 JVM 栈 |
| 迭代启动速度 | 秒级（ts-node/nest start） | 数秒~十余秒（Spring 上下文） |
| 条件装配 | 自定义 Provider 逻辑，无声明式等价物 | `@ConditionalOnProperty` 等注解族 |
| 确定性启动钩子 | `onModuleInit`，但失败语义依框架版本 | `@PostConstruct`，失败 = 上下文拒绝启动 |
| 迁移托管 | TypeORM/Knex 需自行编排生命周期 | Flyway 随 Spring 生命周期自动执行 |
| 强类型审计面 | TS 类型在编译后消失 | JVM 字节码保留，可事后审计 |

### 方案 B：双轨并行（NestJS 生产 + Java 渐进替换）

规划期实际短暂存在的状态。**否决理由**：双轨意味着契约维护 ×2、部署面 ×2、"哪条轨是权威"的持续争论；在 24 个端点的规模上，双轨的成本立刻超过收益。收敛为单轨后，Node 侧以"冻结基线"形态保留——**只读，不维护**。

## 选择 Spring Boot 的理由

以下四条都能指向具体机制，不依赖"Java 更稳"这类无法证伪的表述：

1. **`@ConditionalOnProperty` → 中间件可插拔**。[StateStore 双实现](why-redis-optional.md)按配置装配、回切零代码改动，前提是框架提供声明式条件装配。在 NestJS 中等价物是手写 Provider 工厂逻辑——能做，但每个可插拔点都要重写一遍选择机制，且没有统一的审计面。

2. **`@PostConstruct` → 生产 fail-fast 护栏成为可能**。这是本项目最重要的一道防线：关键配置缺失（JWT 密钥过短、数据目录不可写）或生产档误开 debug 开关时，**应用拒绝启动**而不是带病运行：

   ```java
   @PostConstruct
   public void validate() {
       if (!env.acceptsProfiles(Profiles.of("dev", "test"))) {
           // 生产档：缺密钥 / debug 短信 / 自动建档开启 → 抛异常，拒绝启动
           failFast();
       }
   }
   ```

   它的存在前提是框架有**确定性的启动钩子，且钩子失败能阻断上下文装配**。Spring 的 `@PostConstruct` 失败 = Bean 创建失败 = 应用起不来；这个语义是护栏能成立的全部理由。

3. **Flyway 随框架托管，迁移与启动同生命周期**。不存在"忘了跑 DDL"——迁移在上下文就绪前执行，失败则拒绝启动。对一个没有专职 DBA、迁移靠代码评审把关的团队，这条把一类人为失误直接消灭了。

4. **强类型 + 编译期校验，在契约漂移早期暴露**。在 4.4k 行、24 端点的规模上，DTO 字段改名、返回结构变更会在编译期或启动期报错，而不是在联调时由前端发现。Node 侧同类变更的暴露点是运行时——越晚发现，修复成本越高。

另外，选 Spring 不等于全盘接受其生态——**刻意不引入**的部分同样是决策：不用 Spring Security 完整过滤链（只取 `spring-security-crypto` 单模块做 BCrypt，鉴权用自写拦截器，路径更直白可审）；数据校验用 `spring-boot-starter-validation` 而非自研。**取框架的机制，不取框架的全家桶。**

## Trade-off

### 付出的代价

- **迭代启动速度下降**。JVM 编译 + Spring 上下文装配，本地起服务从秒级变为十秒级；改一行代码重启的反馈循环变长。
  - 缓解：测试以纯单测为主（不拉起完整上下文）；Spring DevTools 热重启按需启用；把"改一行看一眼"的工作模式让位给"测试先行"。

- **双栈残留**。冻结的 Node 基线仍在仓内，构建脚本与契约测试需要同时理解两个栈；新人上手成本高于单栈仓。
  - 缓解：Node 侧目录明确标注"冻结、只读、不接受功能提交"；对拍测试收敛到少数关键契约（如加密互操作），不做全端点镜像。

- **框架魔法需要纪律对冲**。自动配置意味着"谁在什么时候 new 了这个 Bean"不能靠读 `main()` 回答；条件注解组合不当会产生"以为装配了其实没有"的空窗。
  - 缓解：可插拔点收敛到少数接口（如 `StateStore`）并配契约测试；启动期护栏把"装配错误"升级为"拒绝启动"，而不是静默降级。

- **团队技能面收窄**。单轨意味着放弃 Node 后端的持续实践；若未来回到 Node 生态需要重新爬坡。
  - 缓解：接受此代价——技能面收窄是单轨的定义性收益（深度换广度）的另一面；跨语言对拍基线保留了阅读 Node 代码的最小语境。

### 收益

- **四条机制性收益**（条件装配 / 启动钩子 / 迁移托管 / 编译期校验）都可指向具体代码验证，不依赖偏好叙事；
- **运维面收敛**：无 Docker 依赖、中间件减半（见[状态存储 ADR](why-redis-optional.md)）、单进程部署拓扑；
- **审计友好**：字节码保留类型信息，依赖树可用 `dependency:tree` 复核——对需要向外部举证的项目，这比"代码即文档"更硬。

## 后续演进

1. **Node 冻结基线的用途收窄**：只保留跨语言互操作对拍（如加解密逐位对拍）与契约快照，不做功能同步；
2. **Spring 层裁剪继续**：当前未引入 Security 过滤链与对象存储 SDK，后续按管理后台实际需要逐个评估，维持"按需取件"；
3. **若团队规模或生态变化**：单轨决策的复评触发条件是"出现必须用 Node 生态解决的硬需求"（如全栈同构渲染），而非"Node 写起来快"——后者已被迭代速度代价定量抵消。
