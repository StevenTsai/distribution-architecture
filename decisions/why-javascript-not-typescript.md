# ADR: 客户端零构建链优先——JavaScript 而非 TypeScript，自研 store 而非状态库

中文 | [English](../en/decisions/why-javascript-not-typescript.md)

> 状态：已采纳（代价已兑现并记录在案）
> 日期：2026-09（规划 TypeScript + mobx）→ 2026-10（收敛为零构建链）
> 决策者：架构团队

---

## 背景

客户端是微信小程序（原生框架）。规划选型是 **TypeScript + mobx-miniprogram + bindings**——类型安全、状态库成熟。

实施中收敛为 **纯 JavaScript（CommonJS）+ 自研 `store.js`（约 18 行）**，全仓无构建工具、无 npm 运行时依赖。驱动约束只有一个：**小程序开发工具的编辑-预览反馈循环必须是秒级，任何构建链都会在每次保存时插入编译步骤**。

这是一个**主动选择少一层类型保护**的决策。本 ADR 按仓库纪律如实记录：决策依据、已兑现的代价、以及代价兑现后对根因的修正判断。

## 决策

1. **JavaScript（CommonJS），不用 TypeScript**——无编译步骤，产物即源码；
2. **自研 `utils/store.js`（≈18 行：`get` / `set` / `subscribe`），不用 mobx-miniprogram**——`set` 做 `Object.assign` 后全量通知订阅者。

两者是同一条原则的两次应用：**零构建链优先**。mobx-miniprogram 经 npm 引入通常伴随构建打包，与原则冲突；自研 store 把状态库需求压缩到 18 行可审计代码。

## 考虑的替代方案

### 方案 A：TypeScript

| 维度 | TypeScript | JavaScript（本项目） |
|---|---|---|
| 协议数值运算保护 | 编译期类型检查 | 无，靠 review 与测试 |
| 构建链 | 必须（编译 + sourcemap） | 无 |
| 编辑-预览循环 | 每次保存多一步编译 | 即改即预览 |
| 产物可读性 | 产物≠源码，排障需 sourcemap | 产物即源码 |
| 小程序工具链兼容 | 需配置 miniprogram-custom-compile | 原生支持 |

### 方案 B：mobx-miniprogram + bindings

| 维度 | mobx | 自研 store（本项目） |
|---|---|---|
| 引入成本 | npm + 通常需构建打包 | 18 行，仓内自含 |
| 能力面 | observable 深度追踪、computed、action | `get` / `set`（全量通知）/ `subscribe` |
| 状态树规模适配 | 任意 | 本项目状态树浅、页面 ≤16，够用 |
| 心智负担 | 需理解 observable 语义与陷阱 | 无新概念 |

**否决 TypeScript 的真实约束不是"不喜欢类型"**：小程序原生框架 + 零构建链的前提下，TS 的收益（编译期检查）必须以引入编译步骤为代价，而该步骤直接落在编辑-预览循环上——对以协议联调为主的工作模式，这是每天几十次的税。

## 选择零构建链的理由

1. **反馈循环是小程序开发的主成本**。协议联调期的工作模式是"改一帧解析 → 保存 → 真机/模拟器看结果"，单次循环以秒计。构建链把每次循环固定加一步编译——在 24 端点联调持续数周的节奏下，这笔税的总额超过类型检查的收益。

2. **产物即源码 = 真机排障零摩擦**。线上问题直接在 vConsole / 开发者工具里读到的就是源码，不需要 sourcemap 映射。对一个需要在真机上逐帧核对协议解析的项目，这条的日常价值被严重低估。

3. **自研 store 的 18 行是全部心智负担**：

   ```js
   // utils/store.js —— 全部实现
   const state = {}
   const subs = []
   function get(key) { return state[key] }
   function set(key, value) {
     Object.assign(state, { [key]: value })
     subs.forEach((fn) => fn(key, state))
   }
   function subscribe(fn) { subs.push(fn) }
   module.exports = { get, set, subscribe }
   ```

   没有 observable 追踪、没有 computed、没有 action——**状态树浅（页面 ≤16）时，能力过剩的状态库只会带来语义负担**。

4. **性能缺口用调用约定补，且缺口位置可指认**。`set` 全量通知意味着 1s 周期的遥测数据会推整棵数据树；节流收敛到调用侧的 `setIfChanged`（逐字段比对后才 `setData`）。这是**用调用约定补足框架能力**的典型取舍——所有取舍点集中在一个工具函数里，可审可测，而不是分散在状态库的代理语义中。

## Trade-off

### 付出的代价（已兑现，非理论风险）

- **协议数值运算的两处缺陷已在生产路径兑现**：
  1. 16 位有符号数修正读 4 字节字段时的符号扩展错误；
  2. 位移拼接后未补零导致摘要计算错误。

  两类都属于"定长整数运算"，TypeScript 的类型标注**有可能**在编译期拦住第一类（若字段宽度进入类型系统）。

- **全量通知的性能模型依赖调用纪律**。忘用 `setIfChanged` 直接 `set` 遥测数据，不会报错，只会卡——这类缺陷测试环境难以稳定复现。
  - 缓解：`setIfChanged` 收敛为遥测路径的唯一入口并 code review 把关；真机性能采样纳入发版检查单。

- **无编译期契约检查**。前后端字段契约漂移要到联调才暴露。
  - 缓解：契约以 Node 零依赖测试套件双向夹逼（服务端真实实现 × 客户端真实实现打真实 HTTP），漂移在 CI 内暴露而非真机。

### 代价兑现后的根因修正（本 ADR 最重要的一节）

两处缺陷曾被简单归因为"不用 TypeScript 的代价"。复盘后的判断是：**根因是协议层缺少定长整数的统一工具函数**（符号修正、位移、补零各一份实现散落在业务代码里），类型系统只是可能更早暴露它的手段之一。

推论：即使当时用了 TypeScript，只要定长整数工具层缺失，同类缺陷仍会以别的形态出现（比如类型对了、公式错了）。**正确的补救顺序是先建工具层，再谈类型**——事后已将符号修正与位移补零收敛为协议层共享工具函数。

### 收益

- 编辑-预览循环秒级，协议联调期零编译等待；
- 真机排障产物即源码；
- 状态管理全部心智负担 = 18 行 + 1 个节流函数，新人十分钟读完；
- 零 npm 运行时依赖：`git clone` 即可运行，无 `node_modules` 面。

## 后续演进

1. **类型防御的补法不是补 TS**：用 ESLint 规则 + 协议层共享工具函数承接类型系统原本的那部分职责（对魔数、硬编码位宽做静态检查）；
2. **若状态树变深或页面数上量**：自研 store 的全量通知模型先到极限——届时的升级路径是"补细粒度通知"或引入状态库并**同时接受构建链**，两者捆绑决策，不拆开；
3. **本 ADR 的复评触发条件**：出现第二处"若在编译期就能拦住"的缺陷且工具层/静态检查已补齐——届时 TypeScript 的收益才值得重新定价。
